# 服务器 AI 战斗改进设计：预配武器与挖矿自卫

**状态**　三个阶段均已实现，并通过各阶段的隔离专服定向验证。本文承接 Combat MVP 设计，范围限于服务器绑定的独立 AI Player。第一阶段的交付体验是：Agent 配好剑，拿镐开始挖矿；史莱姆靠近并锁定 AI 后，即使模型没有下一轮回复，AI 也能放下镐，用剑还手。

## 改造前的实现与设计取舍

游戏侧已有两种战斗来源。Agent 通过 Lua 提交单目标 `combat_attack(entityRef)`；服务器 Reflex 在模拟更新中寻找威胁，并可在同一次防御中继续处理后续威胁。两者共用战斗任务、身体控制权仲裁和原生攻击。改造前，`Threat` 在遍历 NPC 前检查手持物，`Preflight` 和 `Prepare` 又按手持物校验。镐会被武器判定排除。任务开始后，`ValidWeapon` 持续核对槽位、物品实例和类型。仅修改其中一个入口，仍无法完成拿镐遇敌后的切剑反击。见 [NativeCombatWorld](../CompanionBridge/ServerIpc/NativeCombatWorld.cs)、[AiAtomicActions](../CompanionBridge/ServerIpc/AiAtomicActions.cs)。

TerraBot 的 `BotCombatAgent` 保存主、副、召唤槽，按距离及武器可用性选择主副手，并独立维护仆从。我们采用这种职责分工：Agent 决定可用装备，游戏端决定何时拔出、何时使用。候选范围收窄至 Agent 指定的快捷栏，以便保留工具槽、控制资源消耗，避免背包中新获得的武器意外改变战法。武器适配沿用本项目已支持的原生类别及效果核验。

## Agent 如何配置

以下 API 和字段为拟议契约。配置属于当前 world、actor 和 generation；重新绑定后重新读取并配置。第一版不写入角色存档。

1. Agent 用 `inspect_inventory` 查找武器，再读相关槽位取得新鲜 token。用现有 `swap_inventory_slots` 或 `transfer_inventory_item` 将武器放到选定快捷栏，核对回执后再读快捷栏。在背包动作中使用内部索引，在角色配置中使用游戏按键 `hotbarKey`（1 至 9，0 为第十格）。
2. 新增 `configure_combat_loadout`，一次提交完整的 `primary`、`secondary`、`summon`。每项为 null 或包含 `hotbarKey`、`expectedTypeId` 和本次观察的 `inventoryToken`。例如主武器选键 2 的剑，副武器选键 3 的弓，召唤杖选键 0；键 1 可继续放镐。服务器在游戏线程校验绑定、槽位不重复、物品和已开放角色类型，一次替换配置并返回版本号。任一项无效则保留旧配置。配置本身不换手、不移动物品。战斗中拒绝改配，避免同一任务中途更换授权。
3. 新增只读 `query_combat_loadout`，返回版本、各角色、预期和实际物品类型、当前可用性及原因。token 只用于提交时防旧快照。以后按配置的槽位与类型重新取实际实例，任务接管时再锁定该实例。槽位被换成火把时报告失效；恢复同类型武器后可在下次接战时重新核验。清空全部角色恢复旧版手持武器行为。已有配置但失效时，仅考虑其他显式配置的合格角色。
4. 阶段一只接受普通受支持近战主武器，另外两项须为 null。阶段二开放副武器及已适配的远程、魔法候选，阶段三开放已适配的仆从召唤杖。通过能力握手暴露配置 API 和已支持角色；旧后端继续使用原手持武器契约。Python schema、Lua 白名单、服务器协议和模型说明同步更新。

## 主动攻击与自卫共用的路径

| 环节 | 主动攻击 | 自动自卫 |
| --- | --- | --- |
| 目标来源 | Agent 从观察取得 entityRef，提交现有 combat_attack | 游戏更新检查权威 NPC、目标身份、距离、视线或近期受击证据，保留已有取消抑制和退避 |
| 接战准备 | 校验指定目标，从配置选出可用武器 | 校验当前威胁，从同一配置用同一函数选武器 |
| 控制与攻击 | 两种来源均由同一任务获得身体控制权、切手、核验、接近或瞄准、执行原生攻击 | 同左；防御换目标时重新评估，保留各次遭遇的证据 |
| 结束 | 按指定目标记录终态 | 按当前防御的威胁清除规则记录终态 |

**先判断能否接战，再中断挖矿。** 将威胁识别与武器判定拆开。共用选择函数只读绑定角色、目标和配置，返回候选角色、槽位、实际物品及选择理由，或具体拒绝原因。检查资源和角色限制时使用候选武器。区分“镐的已知可收尾动画”和眩晕、死亡、未知控制者等不可接管状态；不能通过全局放宽 `GameNavigation.Ordinary` 来允许挖矿抢占。近战可接近后出手，入场不要求敌人已经进入挥剑范围。无可行武器时，主动任务报告原因，自卫保留正在执行的任务。

**交接后才切手。** 在仲裁器中复用同一预检，按现有 `task_interrupt_combat` 结束可抢占任务。确认旧任务终态和输入释放，在有界等待内让原生物品使用周期安全结束；记录等待或失败原因。获得唯一控制权后复核绑定、同一目标、威胁（自卫）、配置版本和候选实例。再按既有快捷栏选择语义切换并读回实际槽和手持物，确认后才允许 ItemCheck。允许等待期间持续感知；取消、身份改变、释放未知或超时均禁止继续切手或攻击。交接后目标消失则结束本次任务，已中断的挖矿由 Agent 重新观察后决定是否提交。战后保留最后选中的武器。

**让 Agent 能解释游戏端的决定。** 扩展 `query_combat` 的进度和终态证据，保留 source、目标、原任务 ID、配置版本、所选角色及原因、切换前后槽位、命中归属和输入释放。无可用武器且未创建防御任务时，通过配置查询暴露最近一次自卫预检拒绝的原因和游戏更新号。配置失效、原生未确认与实际击中分别记录。沿用现有 actionId、取消、断线及 unknown 处理。

## 分阶段实施与验收

### 第一阶段：拿镐挖矿时自动拔剑

实施顺序为主武器配置与查询 → 分离威胁检测及只读候选预检 → 改造抢占、接管和战斗武器绑定 → 补齐状态与定向测试。主要入口为 [ServerAiSystem](../CompanionBridge/ServerIpc/ServerAiSystem.cs)、[NativeCombatWorld](../CompanionBridge/ServerIpc/NativeCombatWorld.cs)、[CombatController](../CompanionBridge/ServerIpc/CombatController.cs) 和 [原子操作契约](../python/atomic_operations.py)。本阶段只在入战时切一次，随后沿用既有武器实例锁定。

| 验收场景 | 通过条件 |
| --- | --- |
| 隔离专服：镐在手，另一键放剑，正在执行 mine_target | 先观察到真实挖掘输入或用镐动画，再让可见史莱姆进入现有威胁范围并锁定 AI。此后不提交任何选栏、攻击或模型指令。旧任务因 task_interrupt_combat 结束且释放已确认；自卫任务自行选剑，对同一出生实例产出归属于该 AI 的原生命中，最终按现有规则结束并释放输入。 |
| 同一配置，主动攻击 | 在满足主动获取范围、尚未触发自卫的布置下，拿镐提交 combat_attack。记录 source=agent，与自卫选中同一把剑；只需一次任务提交。 |
| 无效配置与交接失败 | 开战前把剑换成火把：记录槽失效，挖矿继续。交接后目标消失或槽内容变化：无错误攻击。释放未知、取消或角色代次改变：无后续选栏或使用输入。 |
| 兼容 | 无配置且已持受支持武器时，主动与自卫保持旧行为；无配置且拿镐时不擅自搜包。快捷键 0 的读回检查覆盖内部第十格。 |

以游戏更新号记录首次满足威胁、首次检测、旧输入释放、原生周期可切换、实际选中剑、首次攻击输入和首次确认命中。验收检查事件顺序，允许同一更新内先释放再切换，需有阶段顺序证据。平地、无障碍、初始生命和距离固定，分别在镐刚挥出和即将收回时触发。记录各段耗时及首次受伤时刻，证明检测和选剑不等待模型；命中延迟同时受挥镐剩余周期、接近距离和剑动画影响。首轮保留实测基线，再据此设延迟回归阈值。离线定向覆盖预检与交接分支，原生验收扩展 [专服战斗场景](../tests/native_combat.py)；离线通过不能替代拿镐实测。

**第一阶段实装与原生验证（2026-11-18）**　能力名为 `server_ai_combat_primary_v1`。Lua 使用 `api("configure_combat_loadout",{primary={hotbarKey=key,expectedTypeId=row.typeId,inventoryToken=row.inventoryToken}})`；传空表清除配置。副手和召唤角色暂不开放。用 `query_combat_loadout` 读取版本与失效原因，用战斗证据的 `weapon.Selection` 读取抢占来源、受理和选栏更新号。被抢占的挖矿走既有 ActorMining 取消收尾，在确认输入释放和物品周期已清理后交接。

隔离专服使用 tModLoader 2026.9.3.1 和复制世界。Lua 交换木剑至快捷键 0，配置主武器并拿起铜镐。一次实测中，更新 97 观察到挥镐动画、生成威胁并释放挖矿输入，更新 99 选中木剑，115 首次发出攻击输入，129 对该史莱姆造成 6 点原生伤害，257 击败目标。主动攻击也由持镐切回同一把剑；把剑槽换成火把后，服务器记录选武器失败，原挖矿任务完成。该样本覆盖首次挥镐期间遇敌，其他挥镐时机和地形的延迟仍需单独测量。

定向复现：先运行 `scripts/build-companion.ps1 -OutputPath .local/primary-weapon-build`，再在 PowerShell 设置 `$env:COMPANION_COMBAT_CASE='mining-ambush'`，运行 `tests/verify_server_ai_direct_input_native.ps1 -Combat -PackagePath .local/primary-weapon-build/Mods/CompanionBridge.tmod`。每次运行创建独立 profile；查看其中的 `combat-results.json` 与 `manifest.json`。

### 第二阶段：主副武器随交战条件切换

选择器加入射程、射界、弹药和法力。优先使用能有效攻击的主武器；主手暂时够不到或资源不足时，允许能出手的副武器接替。两者均不能立即攻击时，沿用可行的接近或寻找射位逻辑。按原生使用周期切换，在射程边界设置经场景标定的切换余量。每次主动换手建立新的武器绑定，意外换手仍终止。把已发射投射物的武器及目标归属保存在发射记录，不能用命中时的手持物倒推。

验收：同一套剑弓配置，远处可见目标用弓、贴近后用剑；在边界往返时不逐更新抖动；无箭时可用剑接近。专门覆盖“箭在途时切剑再命中”，分别核对箭与挥剑的效果，同槽 NPC 重生或角色换代不得串账。主动与自卫对相同输入给出相同选武器结果。

**第二阶段实装与原生验证（2026-11-18）**　握手出现 `server_ai_combat_secondary_v1` 时，Agent 可在同一次 `configure_combat_loadout` 中提交 `primary` 和 `secondary`。每个角色使用该快捷栏本次观察的 hotbarKey、expectedTypeId 和 inventoryToken；省略角色即清除该角色，空表清空整份配置。服务器先验证所有角色再更新版本，拒绝重复槽位。只有第一阶段能力的后端继续暴露原来的主武器参数。

对于剑与远程武器的组合，两种战斗来源都在近战攻击范围内倾向用剑，在远处有可用弹道时使用弓、枪或已适配的法器。资源不足的武器不能抢占可用武器。相同类别优先使用能生效的主武器。切换使用近战距离内外各 8 像素的余量，并要求几何条件连续稳定 3 个更新；资源耗尽时直接等待当前原生使用周期结束。投射物的命中回执包含发射武器、弹药、投射物身份、所有者、目标代次与发射更新号。

复制世界专服实测（tModLoader 2026.9.3.1，铂金宽剑与木弓）：

| 场景 | 实测 |
| --- | --- |
| 主动攻击、自卫 | 两种来源都先发射木箭，再对同一目标产生原生挥剑伤害。 |
| 箭袋为空 | 未发射投射物，用剑接近并在两次原生命中后击败目标。 |
| 近战边缘、弓射程边缘 | 隔离 fixture 让目标在 51/57 像素、396/402 像素间分别往返。各 96 个原生物品更新样本均保持木弓；在后一组，实际弹道判定交替可射与不可射。目标进一步贴近后切剑。 |
| 最后一支箭在途 | 更新 84 发射、115 切剑、118 命中。命中时手持剑，回执仍归属于原木弓、木箭及同一目标，记录 10 点伤害。 |

复现时将 `COMPANION_COMBAT_CASE` 设为 `dual-weapons`，使用上述隔离专服脚本的 `-Combat` 和本次构建的包路径。fixture 控制目标位置与初始资源，选栏、攻击、飞行和伤害使用游戏侧执行路径。射程数字仅适用于这套装备与测试地形。

### 第三阶段：召唤准备与战中补召

召唤槽独立参与准备和维护。由同一身体仲裁器在空闲或安全窗口检查仆从归属、容量、资源和已支持的杖；缺少预期仆从时执行原生召唤，核对生成后交回武器选择。已有有效仆从时跳过。贴身威胁优先使用能立即还击的主副武器，施法收尾仍遵守原生周期。维持仆从与其派生投射物的独立归属，按实际可核验范围记录战果。

验收：平静时成功补召且不重复施放；仆从已存在、容量不足、法力不足分别给出原因；补召窗口遇贴身敌人时验证切剑顺序。切回剑后分别验证仆从和剑的命中，其他玩家的仆从、已替换目标或旧代次不能贡献本次战果。

**第三阶段实装**　能力名为 `server_ai_combat_summon_loadout_v1`。Agent 可一次提交 `primary`、`secondary`、`summon` 三个互异的快捷键，各角色都用新鲜的槽位 token 和预期类型验证。召唤槽支持史莱姆法杖（仆从容量）与寒霜九头蛇法杖（哨兵容量）。只配置召唤槽也可维护召唤物；需要近身还手时应一并配置主武器或副武器。

绑定角色空闲时，游戏端每 12 个更新检查一次补召条件，并在发出原生使用输入前重新判断危险和资源。正常施法结束后恢复此前仍有效的手持物。已有该角色的同类召唤物时跳过施法；原生生成结果未确认时，本次配置停止自动尝试。`query_combat_loadout` 的 `summon.reason` 返回已存在、容量或法力原因，`maintenance.status` 和 `confirmedCasts` 返回最近一次维护状态和本配置已确认次数。战斗中按目标保留 `contributions.Melee` 与 `contributions.Summon` 的最近一次原生命中，多目标自卫也在对应 encounter 中保留两项证据；哨兵子弹另记录父投射物身份。

**专服复现**　用本次构建包运行相同的隔离脚本，将 `COMPANION_COMBAT_CASE` 设为 `summon-maintenance`。场景先用另一个仆从占满容量，再释放容量并置零法力，然后引入贴身威胁。核对两种拒绝原因及自卫期间零施法。安全后核对一次原生施法、一次法力扣除、召唤物生成以及至少 120 个更新内无重复施法。移除召唤物后在补召动画中引入敌人，核对自然收尾与切剑顺序。最后分别将仆从接触伤害、九头蛇子弹伤害和木剑命中与同一目标的原生记录比对。结果保存在隔离 profile 的 `combat-results.json`。

### 三阶段串联复核

握手含 `server_ai_combat_inventory_v1` 时，`inspect_inventory` 的 full、hotbar、selected、slots 模式会在 `data.combatCandidates` 返回本次检查范围内可配置的普通背包槽和武器类别。按内部 slot 对照物品，整理快捷栏后重新读取 hotbar，再将各行的 hotbarKey、typeId 和 inventoryToken 提交为整套配置。实时 help 提供三槽 Lua 示例；同类候选不唯一时，示例返回需要选择的角色。单独更新一个角色时，想保留的其他角色也须随同提交。

**隔离专服实测（tModLoader 2026.9.3.1）**　将 `COMPANION_COMBAT_CASE` 设为 `loadout-trip`，使用上述 `-Combat` 脚本及当前构建包复现。测试程序从实际背包观察选出剑、弓和召唤杖，交换到空快捷栏，执行实时 help 的配装示例。开挖时背包中的镐临时借用了剑槽。更新 433 敌人出现，挖矿释放输入并归还剑；435 发箭，570 首次用剑命中，802 自卫结束，811 安全补召。抢占预检仅投影同一挖矿任务中仍可按实例归还的物品，接管后仍须校验真实槽位与实例。该场景使用 Lua Worker 和复制世界，无模型请求。
