# 1. 项目最终目标

开发一个能够在 Terraria 世界中像真人玩家一样行动的 AI 第二玩家。

Agent 应当能够：

-   自由移动，决定自己想去的位置。
-   探索地表、地下、洞穴及其他区域。
-   挖矿、砍树、建造、合成和使用物品。
-   应对地形障碍、敌人及环境危险。
-   使用平台、绳索、钩爪等游戏机制解决移动问题。
-   自主选择行动策略，并根据环境变化调整计划。
-   在失败、受伤、死亡后恢复行动。
-   记住过去的探索经历、危险区域和失败经验，并将其用于未来决策。

**核心目标不是让 Agent 永远不犯错，而是让 Agent
具备真人玩家一样的行动、适应、恢复和学习能力。**

例如：

第一次探索矿洞时，Agent 可能因为落差过大而死亡。

复活后，它应该能够记录死亡位置及相关环境，下次探索附近区域时知道这里可能存在危险，并考虑寻找其他入口、搭建平台或使用绳索。

不能简单地因为导航器无法证明路线安全，就禁止 Agent 前往该区域。

# 2. 核心架构原则

## 2.1 Agent 是玩家，其他模块是它使用的能力

Agent 负责： - 理解目标。 - 观察世界。 - 决定行动策略。 -
组合底层能力。 - 根据执行结果调整计划。

控制器、导航器、采矿器、建造器等模块负责提供能力。

不能让导航器成为唯一的移动入口，也不能让某个原子操作的内部限制变成游戏规则。

## 2.2 区分系统安全与游戏风险

必须区分两种约束：

**系统安全约束：** - 控制权归属正确。 - 角色、世界和代次身份匹配。 -
输入正确释放。 - 不确定副作用不能盲目重试。 -
控制租约和动作生命周期正确。

这些约束需要严格保证。

**游戏内风险：** - 下落伤害。 - 生命值损失。 - 未知地形。 - 危险区域。 -
导航搜索失败。 - 暂时没有安全落脚点。

这些应该更多地成为 Agent 决策时使用的信息，而不是一律变成硬拒绝。

游戏中的死亡是正常游戏事件，不等同于系统执行异常。

## 2.3 移动控制与路径规划分离

Agent 不应该必须通过路径规划器才能移动。

简单地形可以直接持续控制方向键和跳跃键。

复杂地形可以使用导航规划。

规划失败后可以尝试其他移动策略，必要时组合挖掘、放置等能力。

模型只提交高层移动意图，底层控制器负责游戏 Tick
中的连续输入和反馈，不要求 LLM 每几帧调用一次 API。

## 2.4 原子操作服务于 Agent，而不是限制 Agent

原子操作应该提供真实、可组合的游戏能力。

其职责是正确执行原生游戏机制、验证实际效果并返回有用信息。

不应因为当前预测器不支持某种地形，就直接把这种地形定义成不可通行。

## 2.5 借鉴成熟开源项目

不以创造独特架构为目标。

优先研究成熟项目的设计和实现，根据 Terraria 的游戏机制进行适配。

# 3. 参考项目

## 3.1 Numen

仓库：https://github.com/Dwinovo/minecraft-numen

本项目重点参考 Numen 的架构和任务设计。

固定研究版本：`61994fc`

重点模块：

  模块               借鉴方向
  ------------------ --------------------------
  RouteSpec          路线策略与行为约束
  Maneuver           移动及地形操作边
  AStar              路线搜索
  HandOver           部分路线交接与可逆性
  Trip               连续移动任务生命周期
  TripMemory         路线搜索和执行反馈记忆
  DigCompanionTask   地形修改后的身体状态恢复
  UnstuckChain       有界脱困机制

重点研究： - 移动任务如何持续执行。 - 如何处理部分路线。 -
如何处理不可逆移动。 - 如何组合移动、挖掘和放置。 -
如何记录失败边和重新规划。 - 如何在执行没有进展时恢复。

Numen 的 Minecraft 物理机制不能直接照搬，需要适配 Terraria。

## 3.2 TerraBot

参考材料：此前提供的 TerraBot 反汇编代码压缩包。

重点研究的模块：

  模块                     借鉴方向
  ------------------------ ------------------
  BotFollowGround          基础地面移动
  BotWideNavigation        复杂地形导航
  BotFollowTraversal       跳跃及越障
  BotFollowRecovery        移动失败恢复
  BotFollowProgress        进展监控
  BotFollowRouteFeedback   路线反馈
  BotPillarRecovery        搭建柱体恢复高度
  BotAutonomy              自主行为组织

特别关注多个控制器如何协作，以及简单地形如何绕过完整路径搜索。

反汇编代码的部分实现需要结合 IL
和实际行为验证，不能把推测当成已经确认的事实。

## 3.3 Terraria 原生游戏机制

最终执行和验证以 Terraria/tModLoader 的真实游戏行为为准。

包括： - 原生角色物理。 - Tile 碰撞。 - 跳跃和重力。 - 摔落伤害。 -
物品使用。 - 挖掘与放置。 - 液体和特殊地形。

## 3.4 DeepSeek 实机测试

DeepSeek 是重要的实际游戏测试员。

它的测试报告和 Trace 用于发现： - Agent 不知道如何使用现有能力。 -
原子操作不符合游戏机制。 - 导航规划不合理。 - 执行结果不准确。 -
缺少失败恢复。 - 观察信息不足。

需要区分模型决策错误、测试脚本错误、游戏适配问题和系统设计问题，不能把所有失败都归咎于
Agent 或导航器。

# 4. 当前项目架构与已有成果

目前保留：

Python Agent + TCP IPC + C# tModLoader Mod。

Lua 作为 Agent 的程序编排语言。

主要能力包括：

-   Virtual Player 单窗口运行。
-   角色身份、生命周期和多人同步。
-   Lua Worker 与原子操作调用。
-   角色状态、背包及地形观察。
-   observe_scene 二维场景感知。
-   地图及探索信息保存。
-   移动、跳跃及基础导航。
-   采矿、砍树、物品使用。
-   Tile 和物体放置。
-   配方查询与合成。
-   死亡、重生和角色持久化。

已有的基础设施应尽量复用，不因路线调整而推倒重写。

# 5. 当前已知问题

以下问题来自此前对 PR #25 的代码审查和 2026-10-30
前后的实机测试记录。它们是后续复核的依据，不代表所有问题在 PR #25 最新
HEAD 上仍保持原状，也不代表都已通过最新版本的实机测试复现。

## 5.1 移动能力与导航

1.  Server AI 目前主要通过 `navigate_to_x` 和
    `navigate_to_landing_region`
    移动，没有独立暴露完整的持续方向控制能力。

2.  `LocalMotionController`
    已经存在，但此前审查时主要支持单段行走或跳跃，不具备完整的路线规划和自主恢复能力；后续已有
    SafeGroundWalk 等改动，当前能力应以最新 HEAD 复核为准。

3.  `NativeNavigation.OrdinaryRejection()`
    对角色状态限制严格，包括装备、Buff、翅膀、火箭靴、钩爪、水中状态等。

4.  `StateSpacePlanner` 存在内部搜索限制，例如 64px
    下降限制、有限搜索预算和局部路线范围。

5.  导航不支持把挖掘、放置等地形修改作为通用路线行动边。

6.  `MinimumSupportPixels`
    支撑判据可能让角色在挖矿后进入导航无法接管的状态。

7.  物理预测器对特殊表面及角色物理状态的支持不足。

8.  导航失败后缺乏独立的移动控制、脱困和策略切换机制。

## 5.2 动作组合

1.  采矿可能破坏当前支撑，使角色无法继续导航。

2.  地形修改前后没有统一的身体状态和站位交接流程。

3.  部分装饰物既被放置预检视为占用，又不在采矿白名单内。

4.  工作台放置受到装饰物占地影响，进而阻断后续合成链。

5.  部分物品使用和战斗能力尚未开放。

## 5.3 感知与记忆

1.  AiMap 目前以每格一个字节保存地图状态，没有完整的逐格时间戳和置信度。

2.  历史地图不能直接视为实时世界状态。

3.  世界时间、天气、事件等查询能力不完整。

4.  死亡日志尚未形成 Agent 可以查询的结构化经验记忆。

5.  缺少统一的失败路线记忆和危险区域经验更新机制。

## 5.4 可观测性与测试

1.  完整 Trace 需要显式开启。

2.  部分早期测试使用直接 LuaRuntime，而非正式聊天 Agent。

3.  这类测试能够评价游戏执行和 Lua
    程序，但不能完整评价模型的自主决策过程。

4.  必须保留原始动作回执、模型请求、工具输出、导航轨迹及游戏状态变化，才能分析真实行为。

# 6. 后续开发路线图

## 第一阶段：自由移动与环境适应

当前最高优先级。

### M1.1 基础移动控制

**当前正在准备设计。**

目标：让 Agent 能够像真人一样直接操纵基础角色移动。

首版固定使用基础角色配置，不考虑复杂移动装备和 Buff。

范围： - 持续向左、向右移动。 - 原地跳跃。 - 移动跳跃。 -
自然下落与落地。 - 主动停止和释放输入。 - 简单地形中的基础移动。 -
通过一次高层操作执行连续移动，不需要模型逐帧调用 API。

要求： - 复用现有 `LocalMotionController` 和游戏线程机制。 - 研究
TerraBot 的 Ground、Traversal、Progress 控制设计。 - 研究 Numen 的 Trip
任务生命周期。 - 移动控制不依赖完整路径搜索。 -
能够返回真实位置、速度、落地和动作终态。 -
失败时提供诊断，不能把模型无法规划等同于角色无法移动。

首版暂不支持： - 翅膀。 - 火箭靴。 - 钩爪。 - 额外跳跃。 - 坐骑。 -
特殊移动 Buff。 - 复杂装备物理。 - 完整复杂地形寻路。 -
自动挖掘和搭建路线。

普通护甲是否纳入基础角色配置，需在设计时单独确定，不应简单继承现有
`OrdinaryRejection` 的限制。

验收重点： - 平地持续移动。 - 双向移动。 - 原地跳跃。 - 移动跳跃。 -
正确停止和释放输入。 - 真实位置与速度反馈。 -
遇到简单障碍时能完成基础越障。 - 不需要模型逐帧调用 API。

### M1.2 复杂地形与移动能力适配

在 M1.1 稳定后开展。

逐步支持： - 平台、半砖和斜坡。 - 冰面、蜂蜜和其他特殊表面。 -
水中移动。 - 翅膀和火箭靴。 - 钩爪。 - 额外跳跃。 - 移动 Buff。 -
其他装备带来的物理变化。

借鉴 TerraBot 的 Capability Signature
思路，角色能力变化后重新评估移动策略，而不是直接拒绝所有非 Basic 状态。

### M1.3 失败恢复与地形修改

目标：Agent 遇到障碍或陷入困难时，可以主动尝试其他方案。

包括： - 有界脱困。 - 后退和重新选择方向。 - 跳跃及绕行。 - 挖掘通道。 -
放置平台。 - 使用绳索。 - 必要时搭建柱体。 -
地形变化后的重新观察和规划。

参考 Numen 的 DigCompanionTask、UnstuckChain，以及 TerraBot 的
Recovery、PillarRecovery。

### M1.4 移动经验记忆

目标：让 Agent 能够从移动失败和死亡中学习。

记录： - 危险位置。 - 跌落事件。 - 死亡位置和可能原因。 - 失败路线。 -
脱困成功的方法。 - 当时的装备、生命和地形条件。

记忆应该包含置信度和适用条件。

地形、装备或能力变化后，旧经验应该重新评估，而不是永久禁止某条路线。

## 第二阶段：完整世界交互能力

补齐真人玩家能够使用的基础游戏操作。

包括： - 挖掘不同类型的 Tile 和墙壁。 - 砍树、锤击。 -
放置普通方块、平台和家具。 - 清理装饰物。 - 开关门、箱子及其他交互。 -
完整物品使用和快捷栏操作。 - 更完整的合成能力。 - 装备管理。

重点是让原子操作能够正确组合，而不是无限增加孤立工具。

## 第三阶段：世界认知与长期记忆

完善： - 地图探索记忆。 - 地图新鲜度。 - 实时状态与历史状态区分。 -
世界时间、天气、事件和群系。 - 资源、矿物、敌人和危险信息。 -
死亡及失败经历。 - 经验检索和策略调整。

## 第四阶段：自主探索与生存

目标：Agent 能够自主决定探索方向和行动目标。

包括： - Frontier Exploration。 - 自主选择未知区域。 -
探索、采矿和资源收集。 - 根据库存和需求选择任务。 - 生命值和物资管理。 -
根据危险和经验改变计划。 - 探索失败后的恢复。

## 第五阶段：战斗与长期游戏目标

包括： - 敌人识别。 - 武器和装备选择。 - 攻击、躲避和战斗控制。 - Boss
战。 - 基地建设。 - 装备成长。 - 长期生存与游戏进度管理。

# 7. 当前开发决策

以下为已经确定的设计方向：

1.  保留 Python Agent + TCP IPC + C# Mod 的整体架构。
2.  保留 Lua 作为程序编排语言。
3.  不推倒重写整个 Agent Loop。
4.  不让导航器成为唯一移动方式。
5.  移动控制和路径规划分离。
6.  首先实现基础角色的移动能力，再考虑翅膀、钩爪、Buff 和装备。
7.  参考 Numen 和 TerraBot 的成熟设计，允许直接借鉴。
8.  以 Terraria 原生游戏机制作为适配依据。
9.  不把预测器和搜索器的内部限制当成游戏规则。
10. 保留真正的系统安全边界，但不要将正常游戏风险全部升级成硬拒绝或
    unknown。
11. 通过真实游戏测试和 Trace 分析问题，而不是仅靠离线测试判断 Agent
    是否会玩游戏。
12. 开发按阶段推进，一次聚焦一个明确目标。

# 8. 后续开发工作方式

每个阶段遵循：

1.  明确当前阶段的玩家能力目标。
2.  研究 Numen、TerraBot 对应实现。
3.  检查当前仓库已有能力。
4.  区分设计缺陷、游戏适配缺陷、模型决策问题和测试问题。
5.  确定 Terraria 适配方案。
6.  形成明确的 Codex 实现任务。
7.  完成定向测试。
8.  DeepSeek 进行真实游戏测试。
9.  分析 Trace、动作回执和游戏行为。
10. 根据证据决定下一步。

不要因为出现单个失败就立即增加新的硬限制。

不要为了测试通过而牺牲 Agent 的实际游戏能力。

评估标准应当是 Agent
能否完成真实游戏任务，而不是新增了多少工具、通过了多少孤立测试。
