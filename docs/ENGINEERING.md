# 工程原则与设计判断

Terraria AI Companion 的目标，是让 AI 以真实玩家身份参与游戏，成为能交流、探索和协作的伙伴。工程选择应服务于可以亲自在游戏中体验的能力。

本文保留跨里程碑的原则、关键决策及其依据。构建命令、API 调用顺序、日志和验收步骤见 [DEVELOPMENT](DEVELOPMENT.md)，当前功能和使用方法见 [README](../README.md)。这里不重复维护操作细节。

## 让软件随需求增长

采用 Growing Software 的方式：从最小可用能力开始，由需求、实验结果和实际问题推动扩展。

M1.0 先验证本地玩家能否右移和停止；M1.1 再解决失焦运行；M1.2 再验证第二个真实客户端的移动能否被真人看到。这种拆分让每次失败都能缩小到具体问题，避免同时调试游戏控制、联机和 Agent 决策。

每次迭代应说明要验证的行为、成功与失败判据，以及尚未涉及的范围。先实现当前需要的最小闭环；Planning、Memory、Skills 等模块在出现具体需求后再引入。正确性、线程边界和控制撤销属于能力本身，不能以原型简单为由省略。

已有结构可以随证据调整。M1.3 为网络请求与游戏更新之间的交接拆出纯 C# 控制状态和 TCP 服务，是新增线程边界带来的需要；这不要求同时建立通用动作框架或 Agent Runtime。重构应解决可说明的问题，并保留相关行为的回归验证。

## 证据决定结论的范围

记录结果时区分以下证据，不把它们互相替代：

| 证据 | 能支持的结论 | 不能单独支持的结论 |
| --- | --- | --- |
| 源码、官方 API 或本机 DLL 的只读 IL 检查 | 在指定版本下的调用路径和约束 | 游戏中一定表现正确 |
| 编译通过 | 当前代码能够构建 | 控制、同步和清理成功 |
| 离线测试通过 | 被测试的协议、状态和线程交接逻辑符合预期 | Terraria 集成或联机成功 |
| 用户游戏实测 | 用户实际观察到的具体行为 | 未执行的场景、其他版本或其他 Mod 的兼容性 |

游戏表现与预期冲突时，先收集失败场景，再核对调用路径。M1.1 的失焦失败改变了输入钩子的选择，也暴露了更早的暂停分支，值得保留其原因。位置日志的端点变化可以支持发生过位移；持续移动、远端可见和真人操作正常，还需要对应的观察。

验证结果应关联版本和场景。M1.0 的手动恢复通过，不能直接证明后续版本无回归；M1.2 的双客户端成功，也不能证明新增 Python 通道已通过游戏验收。

## M1.0–M1.2 留下的设计决策

### 复用真实玩家与原生运动

为了逐步接近原生玩家能力，采用独立客户端承载真实 Player。控制端注入输入，让 Terraria 处理加速、碰撞、减速和联机同步；不直接设置位置或固定速度，不用 NPC 模拟玩家。

M1.0 使用 `SetControls()` 验证了前台右移、再次切换停止和手动操作恢复。当前实现只覆盖水平输入；停止表示不再注入，由原生机制减速，而非强制把速度归零。M1.0 用户还确认开启时 A/D 被覆盖、跳跃保留。

M1.2 已证明两个真实玩家可进入同一世界，A 能观察到 B 的移动与按时停止。这支持继续采用真实客户端和原生同步，但没有验证战斗、背包、饰品或广泛 Mod 兼容性；这些仍需各自实验。

### 分开处理模拟暂停与输入更新

M1.1 最初保留 `SetControls()`，用户发现点击其他窗口后整个游戏停滞。针对本机 tModLoader `2026.08.3.0 stable` 的检查确认了两处不同限制：单人游戏可能在玩家更新前因失焦返回；玩家输入路径也会因失焦跳过 `SetControls()`。仅换输入钩子无法解决整个模拟暂停。

因此改用水平运动前的 `PostUpdateRunSpeeds()` 注入输入，并仅在有效自动控制期间绕过指定的单人失焦暂停条件、临时调整后台休眠。保留真实焦点值，控制结束后恢复休眠设置。安全期限在原生暂停分支之前检查，避免停机保护也被暂停。

用户确认 v0.1.2 失焦后持续右移，约 10 秒后结束，恢复单人失焦暂停。M1.2 则保留多人原生更新路径，不把单人暂停修复扩大到多人。

这里可复用的经验是：先找出执行链在哪里停止，再选择介入点。IL 补丁是当前版本下有实测依据的局部方案，升级后需重新核对；不能把它当成稳定的通用 API。游戏线程完全停止调度时，期限检查也只能等恢复更新后执行。

### 用客户端边界限定控制对象

M1.2 保持 `side = Client`：A 不加载 Bridge，B 单独启用；使用不同的 `-tmlsavedirectory` 隔离角色、配置和测试存档。玩家控制还检查本地身份、游戏模式、连接状态及玩家有效性，排除服务器和远端玩家。

移动同步继续由 Terraria 负责，不新增自定义移动包。用户确认切回 A 后 B 仍移动，A 能看见 B 按时停止，A 自身操作不受影响。同步平滑性、死亡和退出重连后的清理没有因此自动获得验证。

这套隔离依赖部署与代码条件共同成立：安装 Bridge 不等于自动开启控制，但如果在 A 也启用并触发，A 的本地玩家同样可被控制。它不是玩家授权或身份认证系统。

M1.0 曾因快捷键未实际绑定而无法触发。排查时先确认用户能否触达功能、实际配置与日志是否匹配，再判断控制代码；不能仅凭默认键值或 Mod 已加载推断输入已经到达。

## 控制能力必须能够撤销

自动控制默认关闭，只在明确启用且本地玩家有效时施加输入。增加控制来源时，应同时定义优先级、有效期限和撤销路径，避免多个来源争夺同一输入。

当前源码已实现进入/离开世界、死亡、失效和卸载时清理状态，结束控制后恢复临时休眠值。M1.1/M1.2 的手动模式有 10 秒上限，按时结束已有游戏实测依据；完整生命周期场景仍待单独验收。

M1.3 为外部控制实现了以下边界。实现与验证状态分别记录，具体证据和未验证场景集中维护在 [DEVELOPMENT](DEVELOPMENT.md#m13python-control-bridge)，避免将局部成功扩大为全部通过：

- 网络任务只解析协议和提交请求，不操作 Terraria 对象；游戏线程处理请求，网络 I/O 不阻塞游戏更新。
- 外部移动使用短租约；断线或停发后撤销，积压的过期请求不能在稍后获得新租约。旧会话清理不能取消新会话。
- P 可中断外部会话，外部移动不抢占手动模式；显式 stop 可停止任一模式。拒绝移动请求后的清理也不能误关手动模式。

这些是当前实现约束，不是完成安全验证的声明。尤其要区分协议回执、输入已处理与角色实际移动；还要分别测试正常 stop、异常退出和保持连接但不再续期。外部 TCP 当前只面向可信本机，没有身份认证。

相关实现入口为 [玩家输入](../CompanionBridge/Common/Players/CompanionPlayer.cs)、[更新与暂停处理](../CompanionBridge/Common/Systems/CompanionSystem.cs)、[控制状态](../CompanionBridge/ControlState.cs) 和 [TCP 服务](../CompanionBridge/TcpControlServer.cs)。

## 实时控制分层：保留方向，按需求落地

游戏持续更新，模型推理的延迟与失败不能阻塞游戏线程。高频动作和有效性检查应由低延迟、可预测的逻辑执行；LLM 负责适合其响应速度的意图理解、计划和交流。

| 职责方向 | 预期责任 | 当前落地情况 |
| --- | --- | --- |
| Game Runtime | 读取游戏状态、注入原生输入、维护游戏线程及生命周期边界 | Bridge 已实现最小移动控制；完整状态观察接口未实现 |
| Behavior Runtime | 跟随、寻路、战斗、避险和执行反馈 | 未实现；具体边界由任务和实测决定 |
| LLM Agent | 理解意图、高层计划、交流与记忆 | 未实现；当前 Python 脚本仅用于通信与控制验证 |

这张表描述职责方向，不规定现在就建立三个模块或进程。后续需求若要求更合适的拆分，可以调整；执行异步产生的决策前，应重新检查当前状态与时效，不能将旧观察视为仍然有效。

观察接口优先研究 tModLoader 提供的结构化状态，例如位置、生命值、敌人和地形，并按当前任务筛选内容。视觉可作为补充，是否使用由效果、延迟与成本决定。完整观察协议、视觉方案以及向模型提供哪些数据，均尚未落地。

## 把判断留在项目中

影响后续开发的决策应简要留下问题、选择、原因、证据和剩余限制。操作细节与逐项验证状态放在 DEVELOPMENT；当前用法放在 README；跨里程碑仍成立的判断放在本文。改变实现时同步更新相关结论，保留仍有解释价值的失败原因。

文档不能依赖读者知道某次聊天，也不要把设想写成能力。下一阶段从已经证明的行为继续扩展，让架构随着可玩的体验增长。
