# 工程原则（讨论初稿）

> 本文件保存一次项目工程原则讨论的原始草稿，供后续 Codex 结合实际实现与文档整理。它不是已经审定的最终规范。

Terraria AI Companion 是一个长期演进的个人兴趣项目。

目标是让 AI 以真实玩家的身份参与 Terraria，与人类玩家交流、探索、战斗，并逐步具备自主行动能力。

我们希望它最终成为一个真正能玩的游戏伙伴，而不只是展示 Agent 技术的 Demo。

## 1. 让软件随着需求增长

遵循 Growing Software 的思路：从最小的可用能力开始，根据实际需求、实验结果和遇到的问题逐渐扩展。

- 不因为 Agent 通常具有 Planning、Memory、Skills 等模块，就提前实现它们。
- 每次迭代解决一个明确的问题，产生可验证的成果。
- 简单不等于粗糙。已经明确的正确性、线程、安全和生命周期边界不能省略。
- 不以代码量、模块数量或架构复杂度衡量进度。

**让复杂度随着实际能力一起增长，而不是让复杂度先于能力增长。**

## 2. 保持架构可演化

早期设计是当前证据下的选择，不是永久不变的约束。

- 允许新需求推动模块拆分和重构。
- 优先维持清晰的职责边界，不提前构建通用框架。
- 先验证问题是否真实存在，再引入解决机制。
- 不为了复用旧代码而牺牲更合适的设计。
- 不因为担心破坏现有结构而拒绝必要的调整。

重构应该解决实际问题，而不是追求形式上的整洁。

## 3. 让实验驱动技术决策

每个里程碑都应该有清晰的目标和验收标准。

区分以下证据：

- **源码确认**：通过源码或 API 文档确认机制。
- **编译通过**：代码能够构建，不代表行为正确。
- **离线测试通过**：验证了特定逻辑，不代表游戏集成正确。
- **游戏实测通过**：在真实环境中验证了具体行为。

未经验证的假设必须明确标注。

实际游戏表现优先于对代码行为的推测。失败实验同样值得记录，尤其是它改变了我们的技术判断时。

## 4. 区分 Agent 决策与实时游戏控制

Terraria 是一个持续变化的实时环境，LLM 不适合直接负责每一帧操作。

当前倾向采用分层控制：

- **Game Runtime**：读取游戏状态、执行原生玩家控制。
- **Behavior Runtime**：跟随、寻路、战斗、避险与动作反馈。
- **LLM Agent**：理解意图、制定高层计划、交流和记忆。

高频动作应由低延迟、确定性的控制逻辑执行。LLM 负责适合其延迟和能力范围的决策。

模型推理不能阻塞游戏更新。执行过期决策前需要重新检查环境状态。

这是当前设计方向，具体模块边界应由后续实测决定。

## 5. 优先使用结构化游戏状态

由于项目基于 tModLoader，应优先研究游戏内部提供的状态接口，而不是默认依赖截图识别。

结构化状态更适合表示角色位置、生命值、速度、敌人、弹幕和周围地形。

视觉输入可以作为辅助观察手段，但需要根据真实任务评估效果、延迟和成本。

避免将完整游戏世界无差别地发送给模型。观察内容应该服务于当前决策。

## 6. 保留必要的运行时安全边界

随着外部控制能力增加，需要保证：

- 游戏线程不被网络通信或模型请求阻塞。
- 非游戏线程不直接修改游戏对象。
- 自动控制只作用于被明确授权的玩家。
- 连接失效、超时、退出世界或角色死亡时能够安全撤销控制。
- 新功能不破坏已经通过验证的原生游戏行为。

这些要求随着相应功能落地，不需要在项目早期一次实现完整基础设施。

## 7. 记录决策，而不只是记录结果

对影响后续开发的关键决策，简要留下：

- **问题**：当时需要解决什么？
- **选择**：最终采用什么方案？
- **原因**：为什么这样选？考虑过什么替代方案？
- **证据**：由源码、测试还是游戏实测支持？
- **状态**：已经确认，还是仍待验证？

优先在相关代码和 DEVELOPMENT 中记录具体技术细节。本文件只保留跨里程碑仍有价值的原则和关键决策，避免重复维护。

## 8. 保持项目的初衷

这是一个因为热爱 Terraria 与 AI 而启动的项目。

技术方案应服务于最终的陪玩体验，而不是为了展示某种技术而增加复杂度。

允许探索、试错和长期迭代。每个阶段都尽量交付一个可以亲自在游戏里体验的成果。

**我们不是先设计一个庞大的 Agent 系统，再为它寻找用途；而是从真正想要的游戏体验出发，让系统逐渐成长。**
