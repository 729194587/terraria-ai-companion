# G1：Gameplay E2E Baseline（自主玩法端到端基线）

**阶段性质：** 真实能力验证优先，按证据决定是否实现  
**目标后端：** 当前实际使用的 Terraria Agent / MCP 工具链  
**验收环境：** 真实模型 + 真实游戏世界；Dedicated Server 和 Host & Play 分别记录  
**代码基线参考：** `codex/unified-autonomous-navigation`，`30075a4a211293216bfa2aa77028983cea2752ea`

## 1. Objective

先测量当前 Agent 使用现有工具和模型，能否独立完成一个跨多个游戏系统的目标：

> 收集足够的木材，制作一个原版工作台，并放置在附近合适的位置。

这是一次 Gameplay E2E 基线验证，不预设 Agent 缺少规划、Skill、Goal Manager 或底层 API。

**先真实测试，后决定实现。** 在取得真实模型运行证据前，不以“代码中没有专门工作流”“缺少通用 Goal Outcome”或“没有专用 Skill”为理由，推断 Agent 无法完成该目标。

已有用户实测反馈表明 Agent 曾经能够执行工作台放置。这是现有能力的初步证据；本阶段应保留并查明此前测试条件，不重新设计已经可用的放置机制。

## 2. Current Implementation and Evidence

当前代码已经具备完成该目标所需的主要执行能力：

- 场景观察能识别局部树木，并提供 `details.observedTargetTile`。
- `ActorMining` 支持树干目标与斧头选择；`mine_target` 负责接近、重验和原生挖掘。
- `NativeSurvival` 接入原生 `Player.GrabItems`；另有 `collect_drops` 任务。
- `ActorCrafting` 提供运行时配方查询和原生合成。
- `ActorInventory` 提供背包整理、库存 Token 和快捷栏物品操作。
- `place_item` 通过统一原生物品使用路径执行放置；`TileObjectData` 负责多格物体定义，当前工作台有专门的候选观察与验证。
- Agent 已能通过模型决策、`read_skill`、`execute_lua` 和 Program Task API 组合现有能力。

相关代码和已有测试：

- `CompanionBridge/ServerIpc/ServerSceneReader.cs`
- `CompanionBridge/SceneGeometry.cs`
- `CompanionBridge/ServerPlayerRuntime/ActorMining.cs`
- `CompanionBridge/ServerIpc/NativeMineTargetWorld.cs`
- `CompanionBridge/ServerPlayerRuntime/ActorCrafting.cs`
- `CompanionBridge/ServerPlayerRuntime/ActorPlacement.cs`
- `python/agent.py`、`python/lua_agent.py`、`python/program_tasks.py`
- `tests/native_crafting.py`：已有挖掘、掉落拾取等待、运行时配方查询和工作台合成的原生流程，但不是完整真实模型 E2E。
- `tests/native_server_ai_agent.py`：已有 Agent → 模型 → Lua → 原生 Server AI 集成入口。
- `tests/native_server_ai_placement.py`：已有原生放置测试，但主要验证单格放置。

注意：以上是代码能力与既有测试范围，不等同于本阶段的真实模型完整流程验收。代码中的接口缺口也不自动意味着模型无法组合现有接口。

## 3. Test-First Design

### 3.1 测试目标

在当前实际使用的 Agent、模型、MCP 连接和游戏环境中，只发送一次自然语言目标：

> 收集足够的木材，制作一个工作台，并放置在附近合适的位置。

Agent 应自行决定观察、选树、接近、砍伐、拾取、配方查询、合成、库存整理、放置和核验步骤。

测试者只负责建立测试前置条件和启动任务，不逐步指定坐标、工具、材料数量或下一步动作。

### 3.2 测试前置条件

- 使用新 AI 角色或明确记录初始状态的干净测试角色。
- 初始背包没有木材和工作台；记录已有斧头、空余库存槽和其他物品。
- 自然世界中存在可观察的树木和合理的放置区域。
- 不预先发放目标木材或工作台，不直接修改目标游戏结果。
- 记录游戏版本、Mod 包 SHA、世界副本、Agent 版本、模型/模型参数和实际开放的 MCP 工具集合。
- 测试期间不人工给出目标坐标、切换快捷栏或替 Agent 选择下一步。
- 真实模型请求与游戏动作的 Trace / 回执应保存到本地测试证据目录。

如果此前已有符合这些条件的成功测试，优先收集其 Trace、初始/最终状态和环境信息，避免无意义重复。

### 3.3 必须观察的阶段

1. **理解与观察：** 是否正确读取角色、背包、场景和可用工具。
2. **目标选择：** 是否选择真实树木和适用斧头；是否能处理目标不可达或观察不完整。
3. **资源获取：** 是否成功砍树，并通过库存净增确认木材入包；不能只凭掉落物消失判断拾取成功。
4. **配方与合成：** 是否查询运行时配方、判断材料与制作条件，并通过原生回执确认工作台产物进入背包。
5. **库存与放置：** 是否正确整理快捷栏、选择实际观察到的工作台放置候选，并完成原生多格放置。
6. **结束核验：** 是否重新观察世界与背包，并基于真实证据报告结果。

每个阶段记录模型请求、工具调用、Lua 程序、任务 ID、API 结果、动作回执和关键游戏状态。

### 3.4 结果分类

- **E2E 成功：** 工作台确实由 AI 角色制作并放置；原生放置事件、2×1 完整占地、材料消耗、Actor 身份和输入释放均有可信证据。Agent 的最终报告与事实一致。
- **玩法成功但证据不足：** 游戏世界最终结果正确，但现有 Trace / 回执不能充分证明动作归属或完成状态。先补充观测与证据，不要直接改写执行器。
- **部分成功：** 明确记录最后一个成功阶段及第一个失败阶段，保留已完成的游戏效果。
- **失败 / unknown：** 区分模型决策、工具发现、场景理解、导航、采集/拾取、合成、库存、放置、预算、IPC 或游戏同步问题。unknown 不得当作普通失败后盲目重放。

### 3.5 测试矩阵

至少先完成一次真实模型主流程。随后根据首轮结果决定是否需要重复测试：

- 不同树木距离/站位，验证模型能否换目标。
- 木材数量不足或库存空间不足，验证模型是否能继续采集或合理停止。
- 放置候选受阻，验证模型是否能重新观察并选择其他位置。
- 任务超时、取消或 unknown，验证 Agent 是否保留已确认进度并避免重复执行。
- Dedicated Server 与 Host & Play 分别记录；不要将一个环境的结果推广到另一个环境。

## 4. Implementation Policy

**本阶段默认不新增玩法功能。先执行真实测试和源码/Trace 分析。**

Codex 第一轮工作：

1. 阅读本文件及相关源码、测试设施。
2. 查找已有工作台放置和 Agent 端到端测试记录；区分已验证事实、推断与未知。
3. 检查当前 MCP / Agent 实际暴露的工具和能力，不以旧文档或假设代替运行时握手。
4. 准备可复现的测试步骤和证据采集方式；优先复用现有 `native_crafting.py`、`native_server_ai_agent.py` 及原生测试设施。
5. 在环境、凭据和真实模型可用时运行真实模型 E2E；否则交付精确的运行命令、前置条件和待用户执行项。
6. 根据真实结果提交一份简短的 G1 Baseline Report，列出成功阶段、失败阶段、证据位置和确认的根因。

首轮结果出来之前，不把新增 Skill、Goal Session / Goal Manager、通用目标完成判定或新的底层 API 作为预定实现项。

如果真实测试失败：

- 先从 Trace 和实际游戏状态确定第一个阻塞点。
- 检查是否为模型没有发现/正确组合已有工具、上下文或能力描述不清、预算不合适，还是底层 API 真正缺失。
- 能通过模型提示、工具说明或现有 API 组合解决的，不新增执行器功能。
- 只有证明现有能力无法完成目标时，才针对该缺口编写下一份 Implementation Spec。
- 每项修复必须绑定失败用例和回归验收，避免顺手扩大范围。

如果真实测试成功：

- 不为这个目标新增实现。
- 将完整 Trace 和游戏状态证据整理成可复现的回归场景。
- 再选择一个更复杂的自然游戏目标作为下一轮能力评估。

## 5. Testing and Acceptance

### A. 基线证据

- 记录真实模型、Agent、MCP 工具集合、游戏版本和 Mod 包。
- 保存初始/最终背包、关键场景、任务回执和放置证据。
- 能从证据还原每一步决策和动作结果。

### B. 真实模型 E2E

- 只发送一次目标指令。
- 不人工指定中间步骤或坐标。
- 不使用模拟模型结果替代真实模型。
- 根据第 3.4 节分类结果；成功必须由游戏事实和可信回执证明。

### C. 回归

- 复用现有 Python、C#、Dedicated Server 测试设施。
- 只运行与实际发现的问题相关的定向测试。
- 若无代码修改，不要求为了形式执行无关全量测试。

### 通过标准

本阶段的第一目标是取得可信的真实模型 E2E 结论，而不是完成预设代码改动。

- 真实模型完成闭环：G1 基线通过，不新增实现。
- 真实模型未完成：形成有证据的失败定位和下一项最小实现任务。
- 真实模型未运行：状态为未验收，不得用离线或确定性测试宣称通过。

## 6. Deliverables

1. G1 Baseline Report：测试环境、初始条件、真实模型信息、工具调用链、阶段结果和证据位置。
2. 可复现的运行步骤/命令，以及必要的最小测试工具或 Trace 采集改进。
3. 如有真实阻塞，另附聚焦该根因的 Implementation Spec；没有阻塞则不提交玩法实现代码。
4. 更新后的路线图和测试状态。
5. Git Commit：明确区分测试设施改动、真实模型结果和未完成验收项。

本阶段只回答一个问题：**当前 Agent + 当前模型 + 当前工具，实际上能否独立完成这个游戏目标？** 先得到答案，再决定下一阶段做什么。
