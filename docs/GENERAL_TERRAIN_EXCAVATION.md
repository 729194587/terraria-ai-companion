# 通用地形挖掘与动态成本规划

## 1. 目标

建立一套通用的批量地形挖掘能力，使导航与资源采集能够把多个需要破坏的方块作为一个持续任务规划和执行，而不是让
Agent 为每个方块重新发起一次完整任务。

该能力需要支持：

-   以矿物簇等资源目标为单位的采集。
-   导航过程中以障碍物集合为单位的通路清障。
-   根据当前镐子、装备和增益动态估算挖掘时间。
-   将移动、挖掘及必要的地形改造成本纳入路线比较。
-   当玩家挖掘能力或周围地形发生变化时，更新尚未完成的规划。

本设计优先复用当前项目已有的 Terraria
原生挖掘执行、导航和物理模拟，不要求重写这些底层能力。

## 2. 核心概念

### 2.1 两类挖掘批次

两类任务共享批次执行机制，但目标生成和完成条件不同。

#### Target Excavation：目标采集批次

由资源搜索或 Agent 的采集目标产生，例如一簇铁矿、铜矿或其他资源。

-   批次包含一组需要采集的目标方块。
-   目标方块以集合形式管理，不要求 Agent 逐格提交任务。
-   规划器寻找能够触及多个剩余目标的工作位置。
-   当前工作位置没有合适的剩余目标时，再评估是否移动到其他工作位置。
-   以目标集合完成或明确报告部分失败作为任务结果。

#### Route Clearance：通路清障批次

由导航规划器产生，目标是清除抵达目的地所必需的障碍。

-   批次只包含当前通路方案中确实需要清除的障碍。
-   不应把附近所有可挖方块都纳入清障任务。
-   需要考虑角色身体空间、支撑关系、落脚位置和清障后的地形变化。
-   清障后重新确认通路是否成立；若地形或角色状态变化使原计划失效，应更新剩余工作。

### 2.2 共享执行机制

两类批次可以共享以下能力：

-   批次生命周期和剩余目标管理。
-   工作位置评估。
-   工具选择和挖掘成本估算。
-   调用现有原生单方块挖掘机制。
-   逐目标验证实际破坏结果。
-   地形变化后的状态更新与必要重规划。

共享执行机制不意味着两类任务使用相同的目标选择规则。资源采集以完成资源目标为目的；通路清障以建立可通行路径为目的。

## 3. 批次执行器

批次执行器负责管理一组挖掘目标的持续工作过程。

建议的生命周期：

1.  接收目标集合及任务类型。
2.  验证目标当前是否有效、可挖掘。
3.  根据剩余目标和当前角色状态评估工作位置。
4.  选择当前工作位置可触及的目标，并确定执行顺序。
5.  通过现有原生挖掘机制执行单个目标。
6.  验证该目标是否实际被破坏，并更新剩余目标。
7.  重新观察角色、地形、目标和挖掘能力状态。
8.  当前工作位置仍有合适目标时继续；否则评估移动到其他工作位置或重新规划。
9.  全部目标完成后返回成功；无法继续时返回明确的部分完成或失败结果。

关键要求：

-   批次状态应跨越多个单方块挖掘动作持续存在。
-   Agent 不应为批次中的每个方块重新启动完整任务。
-   每个方块仍需有独立的实际破坏验证。
-   不得仅凭输入已发出或预计时间已到就认定目标完成。
-   目标已被其他原因破坏、移动或变得不可达时，应更新批次，而不是误报成功。
-   挖掘输入可以在相邻目标之间尽可能保持连续，但必须遵守 Terraria
    原生工具、瞄准、攻击间隔和输入状态规则。
-   当需要切换工具、移动站位或处理不连续目标时，允许正常释放和重新建立输入。

## 4. 工作位置规划

对于包含多个目标的批次，规划器应评估工作位置，而不只是选择与某个目标直线距离最近的位置。

评估因素至少包括：

-   从当前位置抵达候选工作位置的实际导航成本。
-   候选位置能够触及的剩余目标数量。
-   从该位置完成这些目标所需的预计挖掘时间。
-   完成当前可触及目标后，抵达其他工作位置的成本。
-   角色碰撞空间、支撑、液体、危险和落脚条件。
-   清除目标后地形变化对后续移动及工作位置的影响。

优先复用现有安全站位检查、SurfaceGraph、物理模拟和导航能力。

规划目标应从"抵达一个预先选定的最近站位"提升为"在可行工作位置集合中比较完成剩余目标的总体成本"。

不要求无条件优先走路，也不要求无条件优先挖掘。应比较实际可行方案的预计总代价。

## 5. 动态挖掘成本模型

### 5.1 统一估算目标

建立统一的挖掘时间估算机制，供以下场景共同使用：

-   选择挖掘工具。
-   评估采集批次的完成时间。
-   评估导航清障成本。
-   比较挖掘开路与绕行方案。
-   估算批次剩余工作量。

成本应使用统一的时间单位，例如游戏更新帧或项目中已有的等价时间单位，避免不同模块各自使用无法比较的公式。

### 5.2 需要考虑的因素

至少检查并纳入适用的原生因素：

-   目标方块的原生挖掘规则及所需破坏量。
-   镐子的镐力。
-   镐子的工具速度及相关前缀属性。
-   玩家当前有效挖掘速度。
-   装备、药水、增益及其他会影响挖掘速度的状态。
-   工具切换、动作启动等必要开销。

应以当前项目绑定的 Terraria
版本和原生实现为准。不要仅凭属性名称推导公式，也不要把普通近战速度加成直接等同于挖掘速度加成。

### 5.3 工具选择

在能够合法破坏目标且满足实际使用条件的工具中，依据预计完成时间选择工具，而不是只比较单次命中伤害或镐力。

如果不同工具的切换成本会影响批次总时间，也应纳入批次级评估，避免在相邻目标之间无意义地频繁切换工具。

### 5.4 动态能力状态与规划失效

建立能够反映当前有效挖掘能力的状态快照或指纹。

当以下状态变化影响预计挖掘时间时，依赖旧能力数据的规划应失效或重新评估：

-   更换镐子或工具前缀变化。
-   玩家装备变化。
-   获得或失去挖掘药水及其他相关增益。
-   玩家有效挖掘速度发生变化。
-   其他会改变原生挖掘结果或耗时的状态变化。

不能只依赖背包物品指纹判断能力是否变化；还应检查玩家当前有效挖掘属性。

批次执行期间若能力发生变化，应重新计算剩余目标的成本。已经完成的工作不需要重新计算。

## 6. 与现有系统的关系

实施前应以当前分支源码核实实际职责和调用关系。以下是优先检查和复用的现有模块：

-   `ActorMining`：原生单方块挖掘、工具使用及实际结果验证。
-   `LocalTerrainPlanning`：局部地形编辑与候选动作规划。
-   `NativeNavigationEdits`：导航过程中的挖掘、放置及地形改造。
-   `NativeNavigationWorld`：导航规划生命周期、移动与地形编辑协调。
-   `SurfaceGraph` / `SurfaceNavigator`：现有地表路线搜索。
-   现有物理模拟与安全站位检查。

设计方向是补充批次级任务管理、统一成本估算和多目标工作位置评估，尽可能复用现有底层能力。

## 7. 参考项目的借鉴范围

### Numen

重点参考：

-   `DigCompanionTask` 的多目标持续任务组织。
-   `Destination.cells()` 和 `Goals.dig(List)`
    的多目标工作位置表达与选择。
-   `CostModel` 对移动、挖掘等行为进行统一成本比较的思路。

Numen 的机制需要适配 Terraria 的物理、工具和原生挖掘规则，不应直接照搬
Minecraft 的数值或运动假设。

### TerraBot

重点参考：

-   `UseAt()` 一类持续维持原生使用输入的方式。
-   `GatherTile()` 一类在自主工作循环中切换后续目标的方式。
-   `BotWorkPosition.TryFind()` 对目标附近可工作位置进行检查的思路。

当前项目已经具备 Terraria
原生持续挖掘执行基础，应优先复用，不要重复实现另一套底层挖掘器。

## 8. 验收标准

### 批次执行

1.  多方块矿物簇能够作为一个批次完成采集。
2.  导航通路中的多个必要障碍能够作为一个清障批次处理。
3.  Agent 不需要为批次中的每个方块重新发起完整任务。
4.  每个目标都有明确的实际破坏验证。
5.  批次能够正确区分完成、部分完成、中断和失败。
6.  地形或目标变化后，剩余工作能够正确更新。
7.  在不需要移动或切换工具时，能够尽可能保持连续挖掘输入。

### 成本与规划

1.  不同镐子对同一方块能够得到基于原生机制的合理预计挖掘时间。
2.  挖掘速度增益能够反映在预计成本中。
3.  工具选择依据预计完成时间，而非单纯比较镐力。
4.  导航清障和采集使用一致的挖掘成本基础。
5.  挖掘能力变化能够使旧规划重新评估。
6.  多目标工作位置评估能够减少不必要的移动和重复导航。
7.  能够比较可行的绕行与挖掘方案，不把某一种行为设为无条件优先。

## 9. 实施拆分

-   **任务 A：动态挖掘成本模型。**
    统一预计挖掘时间、工具选择、导航成本和能力变化后的规划失效机制。
-   **任务 B：通用批次挖掘执行器。**
    支持目标采集批次与通路清障批次，并实现多目标工作位置管理和持续执行。

建议先完成并验证任务 A，再实施任务
B。两项工作分别测试，最后进行集成与真实游戏测试。
