# M3：Program Runtime 与游戏任务协作

## 设计与实现说明（Codex 实施基线）

-   目标：完善 Terraria AI 的 Program / Task 协作，使 Agent
    能编排持续运行的游戏任务，并可靠处理中断、结果交接与最终反馈。
-   审查依据：第三模块 C1--C5（含 C5-A--C5-E）。
-   Terraria
    审查代码基线：`09bb4fef86a32519496363c7c20e6ef63f36fc79`。该提交仅用于追溯审查结论，不代表实施目标分支或当前
    HEAD。
-   Numen 对照：`1a90f11c1ecbbda662c5a8fc0629c667bd519db3`。

------------------------------------------------------------------------

## 1. 要解决的问题

当前项目已经具备 Python Agent Loop、Lua Worker/Runtime、工具分发、C#
游戏侧 Task Runtime，以及 `mine_target`
等复合任务。动作身份、执行证据、取消清理和 `unknown`
保护也已经有相当基础。

当前主要问题是这些能力还没有形成足够清晰的协作模型：

1.  **Program 与身体任务耦合。** 长时间游戏操作仍容易占用整个 Lua
    Program；Program
    结束、被取消或被新聊天替代时，已受理任务如何继续缺少统一契约。
2.  **任务协调不完整。** Agent
    需要能够获知活动任务、等待指定任务、接收任务结束结果，并处理 Program
    已结束后才到达的结果。
3.  **执行中断缺少完整闭环。**
    寻路或执行任务时可能遇到敌人、危险环境、无进展或新指令。系统需要安全停止/抢占、报告情况，并在条件允许时恢复或交还
    Agent 决策。
4.  **结果层级存在耦合。** Run、Program、Action、Task、Goal
    的结果不能相互替代。当前实现中，最终 LLM
    请求失败可能影响已经完成的游戏任务结果。
5.  **最终反馈不够可靠。**
    游戏动作已经完成但模型无法生成最终回复时，系统仍应向玩家准确说明已确认的执行事实；不能丢失事实、夸大进展或重放动作。

M3 的目标是让系统形成以下闭环：

**Agent 决定目标 → Program 编排 → 游戏 Task 独立执行 →
任务状态与结果返回 Agent → Agent 根据新事实继续决策并向玩家反馈。**

## 2. 目标架构与职责

沿用现有 Python Agent、Lua Program、C# 游戏执行层的分层，不为追求与
Numen 相似而重写现有模块。

-   **Python Agent：** 负责目标决策、模型调用、Run
    生命周期、上下文、任务结果消费和玩家沟通。
-   **Lua Program：** 负责顺序、条件、循环和有限的任务编排；调用宿主 API
    获取观察结果或提交游戏任务。
-   **C# 游戏任务运行时：** 负责任务受理、游戏 Tick
    中的实际执行、身体控制权、动作停止/释放、效果验证和权威任务结果。
-   **Python/C# 之间的桥接层：**
    负责提交、查询、取消和传递结果，不应形成与 C#
    相冲突的第二份任务权威状态。

Numen 值得借鉴的是 AgentLoop、Program、Task
的职责分离，以及任务完成结果能够在程序生命周期之外继续交接的思想。具体类结构、事件组织和接口形式应根据当前仓库实现选择。

## 3. 必须满足的关键契约

### 3.1 生命周期独立

Run、Program、Action、Task、Goal 分别表达不同事实：

-   Run：一次 Agent 执行如何结束。
-   Program：一次 Lua 程序如何结束。
-   Action：某次具体动作如何结束。
-   Task：游戏侧受理的任务如何结束。
-   Goal：玩家目标是否得到证据支持。

必须保证：

-   Program 正常结束不代表 Task 或 Goal 完成。
-   已受理的 Task 不因创建它的 Program 结束而自动丢失。
-   模型请求失败只影响相应 Run，不得改写已经验证完成的 Task。
-   Task 完成不自动等于玩家 Goal 完成。
-   `GoalOutcome=partial`
    必须有目标相关的已验证进展；选择工具、切换快捷栏等准备动作不能单独构成目标进展。

### 3.2 任务提交、等待与结果交接

长时间、不适合占用整个 Program
的游戏操作，应能够以独立任务形式提交。Program
可以等待指定任务，也可以在适当情况下结束，而任务继续由游戏侧运行时推进。

无论采用 JOB/Await 还是其他等价实现，都必须保证：

-   提交结果能明确区分确定未受理与受理状态不明。
-   每个任务有稳定身份，等待和查询针对明确的任务身份。
-   等待超时不自动等于任务执行超时，也不应未经明确策略就取消任务。
-   Task 完成后，即使原 Program 已结束或不再等待，结果仍能交给 Agent。
-   任务结果能够去重；迟到结果不能覆盖更新的状态或被重复结算。
-   Agent 新一轮决策能够获知当前活动任务和尚未消费的重要结果。

### 3.3 中断、抢占与恢复

任务执行期间可能发生新聊天、明确停止指令、敌人或环境危险、无进展等情况。

必须明确区分：

-   普通新聊天替代旧 Run/Program；
-   玩家明确要求停止任务；
-   身体任务因突发情况暂时让出控制权；
-   任务无法安全继续或执行结果不确定。

具体处理应符合以下行为：

-   不得仅因 Run/generation 变化就静默丢弃已受理 Task。
-   明确停止指令应进入任务取消流程；只有获得可信终态及必要的输入释放证据，才能报告已停止。
-   突发危险应优先保证身体控制安全，并把结构化原因和任务状态交给
    Agent；不应依赖 LLM 每 Tick 处理危险。
-   只有在原动作已安全结束、身份和环境重新验证、任务仍可继续时，才允许恢复。
-   无法确认执行状态或释放情况时保持 `unknown`，不得自动重放。
-   新目标与当前任务冲突时，应有明确的取消或替换结果，不能静默覆盖活动任务。

M3
需要实现可验证的最小中断/抢占处理路径，但不要求在本阶段完成完整战斗策略。

### 3.4 结果语义与最终回复

必须修正审查中发现的结果耦合：

-   Run 失败不能污染已完成的 Program/Task 事实。
-   各层结果独立计算，不能用 Run 是否正常结束来推断游戏 Task 是否完成。
-   目标部分完成必须依据目标相关证据，而不是"存在任意成功动作"。
-   多个重要事实同时存在时，最终回复不能因单一优先级分支而遗漏关键失败或未确认效果。
-   最终回复应受宿主确认的结构化事实约束，不能仅依赖正则表达式过滤成功声明。
-   如果动作已经完成而最终 LLM
    请求失败，宿主应能生成简短、准确的兜底回复；不得把已完成任务降级，也不得重新执行动作。
-   `unknown`、效果未确认、身份不匹配和输入释放不确定必须如实表达。

## 4. 实施范围

本次围绕上述问题完成必要的架构调整和实现。

优先顺序：

1.  **先修正结果契约。** 分离 Run、Program、Action、Task、Goal
    的结果计算；修复 Goal partial
    判定；补齐动作完成后模型失败的事实反馈。
2.  **再完善 Program 与 Task 协作。** 使长时间游戏任务能够独立于 Program
    推进，并提供明确的提交、查询/等待、取消和结果交接能力。
3.  **完善任务协调与突发中断。** 处理活动任务与新 Run
    的关系，建立安全的中断/抢占及条件恢复路径；对危险、无进展等情况能够安全处理并向
    Agent 反馈。
4.  **完成端到端验证。**
    覆盖正常执行、部分失败、中断、unknown、迟到结果和模型故障。

这是问题解决的优先顺序，不限定必须拆成几个
PR，也不要求按某种类结构实现。

## 6. 验收标准

实现至少应通过以下场景验证：

  --------------------------------------------------------------------------------------------------
  场景                                验收结果
  ----------------------------------- --------------------------------------------------------------
  正常执行                            Agent 提交游戏任务，任务在游戏侧推进，终态能返回 Agent
                                      并形成准确回复

  Program 结束                        Program 结束后，已受理 Task 按任务策略继续；结果不会丢失

  部分失败                            已完成的子任务和证据保留；准备动作不被算作 Goal 进展

  新聊天到达                          旧 Run/Program 被替代时，活动 Task 有明确处理结果，新 Run
                                      能获知其状态

  明确停止                            任务进入取消流程；只有确认终态和必要释放证据后才报告停止成功

  突发危险                            当前任务能安全停止或让出控制权，Agent
                                      收到结构化情况；恢复前重新验证必要条件

  unknown                             ACK、身份或释放证据不确定时保持 unknown，不自动重试或重放

  迟到结果                            原 Program 已结束后到达的 Task 结果仍能交给
                                      Agent，且不会重复结算

  模型故障                            游戏 Task 已完成但最终 LLM 请求失败时，Task 仍保持
                                      completed，宿主准确兜底且不重放动作
  --------------------------------------------------------------------------------------------------

同时运行相关 Python/C#
定向测试和构建检查。实机测试与离线替身测试应分别记录，不得混为一谈。
