# 多人原子操作确认

部分客户端原子操作需要服务器权威确认。客户端能力握手只表示客户端具备协议实现；实际动作还必须确认服务器端支持并完成相应原生处理。

## 适用操作

当前服务器确认路径覆盖：

- `mine_wall`
- `place_wall`
- `hammer_tile`
- `interact_tile` 的受支持原版门、宝箱、开关和拉杆交互

这不自动改变 `mine_tile`、`place_tile` 或 `attack_entity` 的完成语义，也不开放任意 Tile/ModTile 网络修改。

## 执行流程

`Python 校验与能力检查 → 客户端动作控制 → 原生输入/交互路径 → 捕获本动作拥有的原生请求 → 服务器游戏线程重新校验 → Terraria 原生网络处理器 → 服务器状态核验 → 状态同步 → 客户端收敛确认 → 动作终态与输入释放证据`

请求绑定客户端/服务器世界会话、Actor/Session/Generation、ActionId 和 nonce。服务器身份来自实际 Mod 包发送者，不接受载荷自报身份。Arm 只允许动作进入受控执行阶段，不是效果完成证据。

服务器在执行前重新检查玩家生存状态、权限、选中槽/物品、目标快照、距离、区块加载和原生对象范围。执行通过 Terraria 原生消息处理和 Mod 钩子完成，不直接赋值 Tile/Wall 伪造效果。

## 操作完成证据

| 操作 | 服务器侧核验 |
| --- | --- |
| 挖墙 | 目标原有墙被本动作移除 |
| 放墙 | 目标出现预期墙类型，服务器实际消费恰好一件物品 |
| 锤击 | 原生方块/平台形状发生预期变化；仅 Frame 美术变化不算成功 |
| 门 | 实际门状态转换，客户端状态一致 |
| 宝箱 | 服务器玩家箱子状态与客户端打开/关闭状态一致；不包含箱内搬运 |
| 开关/拉杆 | 原生对象仍是目标类型且 Frame 状态变化；不证明下游电路效果 |

多格对象按 TileObjectData 锚点和完整占用范围验证。物品消费需要服务器槽位变化与客户端同步结果一致，避免将客户端预测消费和服务器消费重复计算。

## 取消、重复请求与 unknown

- 每个请求使用有界身份槽、租约和绝对截止；重复 Execute 不得重复执行或再次消费。
- 取消在服务器执行前生效时可返回 cancelled；原生效果已经发生时，迟到取消不能撤销效果。
- 客户端取消、断线或超时若发生在服务器结果未知时，保留 pending/unknown，不报告 completed，不自动重试。
- 服务器已报告完成但客户端状态未在期限内收敛，仍是 unknown。
- 只有服务器效果、客户端状态一致和客户端输入释放证据都已确认，才允许报告 completed。
- unknown 后应重新观察世界与背包，再由 Agent 决定下一步；不要重复拨动开关、拉杆或放置/消费动作。

## 运行边界

服务器与参与客户端必须加载兼容版本的 CompanionBridge，并在握手中确认对应能力。专用服务器和主机开服是不同运行形态，应分别验收。Agent TCP 控制连接仍属于受控客户端；不要把客户端本地 TCP 端口当成服务器端控制端口。

## 代码入口

- 客户端动作与控制状态：`CompanionBridge/ControlState.cs`、`CompanionBridge/TcpControlServer.cs`
- 服务器原生处理与身份确认：`CompanionBridge/ServerPlayerRuntime/`、`CompanionBridge/ServerIpc/`
- Python 能力和回执：`python/atomic_operations.py`、`python/server_ai.py`
