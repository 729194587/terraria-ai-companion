# 导航系统

## 职责划分

Agent 选择目的地和策略；Lua 组织观察与动作；导航运行时负责在当前运动能力和观察范围内规划、执行、监测实际状态并核验落点。导航器不负责全局探索、采矿、建造或战斗策略。

## 主要操作

- `navigate_to_x`：沿水平方向导航到玩家碰撞框左边缘的目标世界像素 X。目标语义是水平穿越/到达，不是精确 XY 站位。
- `navigate_to_landing_region`：导航到观察结果提供的二维落脚区域。目标描述玩家左边缘 X 区间和脚底表面 Y；只接受当前执行器支持的落脚面。
- `move_input`：服务器 AI 的有界原生方向输入。它不做路径搜索或安全落点证明，撞墙、走下边缘或受伤都是可能的真实结果。需要受控导航时优先使用导航操作。

## 执行模型

规划基于当前 Player 物理状态、已验证的 Mobility Profile 和局部碰撞世界。搜索器输出有限的安全动作路线；执行器逐帧根据当前世界和实际 Player 状态重新核验，不盲目播放旧输入序列。

导航任务保留目标、Actor/World/Generation 身份、截止时间和进展预算。局部路线结束后可从真实状态继续规划；计划检查点必须经过实际位置、速度、支撑和跳跃释放确认。预测到达不等于真实到达。

服务器 `navigate_to` 的根任务和内部移动以已核验进展续期。根任务无进展租约为 2700 游戏更新，常规移动子任务为 1800 游戏更新。分帧搜索不计为身体停滞。移动累计 1800 个实际位移更新后，下一个安全停稳点可生成 `native_navigation_work_checkpoint` 回执，父任务从真实站位继续同一目的地。根请求仍受 180 秒墙钟监督上限约束，Lua Program 的预算独立生效。

地表图和局部物理状态搜索的容量为约 40000 项，保留原有分帧执行。地表图达到容量时仍尝试已有候选，无法给出可验证路线时报告预算耗尽。普通局部物理搜索保持 192 像素水平、128 像素垂直范围。一个已验证且朝低处目标前进的下降边可越过垂直窗口，后续搜索从实际落地重新开始。

## 浅水通行

普通运动角色可从陆地走入有支撑的浅水，沿水底移动，并用原生跳跃上岸。地表图把水中的较慢水平位移计入路线估价，局部搜索用预测输入帧数核验连接。预测分别使用更新开始时的湿身状态和原生碰撞探测，保留入水和出水的跨帧过渡。原生水碰撞在裁剪速度后将未受阻的位移减半，保留速度供下一个更新使用。

水域路线仍要求安全落脚，头部浸没、特殊涉水装备和不受支持的水中运动组合不在当前范围。岩浆、蜂蜜和微光各自保留接触拒绝。地形改造仍使用原有液体检查。

## 安全检查

- Player、Tile、Collision 和输入操作都在正确的游戏线程执行，并绑定独立 Server AI Actor。
- 未知地形、危险格、未加载区域和超出采样范围不能当作空地。
- 落脚确认要求真实支撑、可接受速度和跳跃释放；未确认的落地保持 unknown。
- 普通重力下按原生身体顶部 Tile 行和 `fallStart` 比较 `25 + extraFall`。原生 `noFallDmg`、已装备翅膀和已确认的免落伤表面可免除该伤害。下降仍受局部碰撞采样和支持范围约束。执行前复核当前能力、预计落点和下一帧的碰撞；能力丢失时释放输入并尝试在安全落脚后重新规划。
- 运动能力变化会使旧计划失效；未知装备、Buff、坐骑、额外跳跃、翅膀或第三方 Mod 行为不自动视为受支持。
- 路线偏差可按当前恢复策略停止、释放输入并从真实状态有限重规划。只有宿主为特定已知失败明确授予 `continuationAllowed=true` 和允许的 continuation scope，Agent 才能按该范围重新观察并尝试有界 `move_input`；不能根据 reason 文本自行降级。恢复预算耗尽、危险或身份失效时终止。
- 取消、超时和断连必须释放输入。释放输入不代表角色已经停稳或到达目标。

## 已知范围

导航是局部、有界的，不保证全局可达、最短路径或对任意自然世界路线成功。深落差、液体、复杂机关、动态敌人干扰、特殊装备和任意 Mod 运动行为只有在明确支持并验证后才能使用。局部搜索预算耗尽不能解释为整个世界不可达。

`mine_target` 会把导航作为游戏侧任务的内部子任务；其生命周期和挖掘目标重验见 [任务运行时](M1_TASK_RUNTIME.md)。

## 实现入口

服务器自主 `navigate_to` 的持续内部移动已加入 Phase 2 Surface Graph：在游戏线程增量采集较大范围地形，以落脚区间和 walk/jump/drop 候选图组织局部目标，再交给已有物理规划器验证。原生碰撞窗口、根任务串行挖掘/放置、真实落地确认及身份/取消保护继续复用。短程地面接续保留原有精确制动规划。预算、未知覆盖和局部无路线分开报告；图未找到路线不证明全局不可达。

具体映射、范围、定向证据和限制见 [Phase 2 实现记录](PHASE2_SURFACE_GRAPH_IMPLEMENTATION.md)。

Phase 3 v1.1 在原根任务中加入有限连续改造评估：在彼此独立的虚拟地形上估算连续挖掘、放置及组合成本，与真实地形移动路线比较；每次只执行下一项原生动作，确认真实变化后重新观察。虚拟结构不构成原生碰撞证明，也不会写入真实 Tile。范围与定向证据见 [Phase 3 实现记录](PHASE3_LOCAL_PLANNING_IMPLEMENTATION.md)。

Phase 4.1 在原有 `MobilityProfile` 中提供原生运动能力和环境状态的只读值快照，保留 ExtraJump 原生顺序、功能性翅膀、火箭靴、坐骑及钩爪身份。资源采样与规划版本分离；发现特殊能力不会增加可用导航模式。实际采集边界、双引擎验证和限制见 [Phase 4.1 实现记录](PHASE4_1_MOVEMENT_DISCOVERY_IMPLEMENTATION.md)。

Phase 4.2 在现有物理状态、地面动作搜索和逐帧执行上接入单一已验证的 Cloud ExtraJump 模型。只有动态快照中单独启用该能力、且没有阻止额外跳跃时才参与规划；计划通过真实松键/再按下请求原生触发，并核验 Active、Available、jump 计数及运动状态。正常消耗/结束/落地刷新保持规划版本，异常变化仍走释放、落地核验与恢复。范围、证据和手动验证见 [Phase 4.2 实现记录](PHASE4_2_EXTRA_JUMP_NAVIGATION_IMPLEMENTATION.md)。

Phase 4.3 在同一预测与执行链上加入普通天使翅膀和基础火箭靴脉冲模型。有功能性翅膀时始终使用翅膀策略，耗尽后也不切到火箭靴；没有翅膀才考虑推进。飞行时间、推进资源和延迟进入物理搜索状态，原生观察核验与安全恢复继续复用。只对经过完整安全落脚尾段验证的小幅空中偏差进行反馈修正。后续 P3 扩展了普通非悬停翼型。2026.09.3.1 隔离服务器已验证天使翼、骨之翼上高台和骨之翼经中间平台跨两个缺口；当前测试使用 `verify_navigation_recovery_native.ps1 -Wings`。早期火箭靴与飞行模型的证据见 [Phase 4.3 实现记录](PHASE4_3_WINGS_ROCKET_BOOTS_IMPLEMENTATION.md)。
