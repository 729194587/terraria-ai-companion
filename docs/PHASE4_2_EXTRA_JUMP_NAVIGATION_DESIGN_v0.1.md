# Terraria 自主导航系统 Phase 4.2：ExtraJump 导航接入 MVP 设计

**版本：** v0.1\
**状态：** 设计草案，待审查；尚未交给 Codex 实现\
**代码基线：** `codex/unified-autonomous-navigation`，提交 `d238728`\
**前置阶段：** Phase 1--3、Phase 4.1\
**参考：** TerraBot 源码压缩包、Numen、tModLoader 原生 ExtraJump 机制

------------------------------------------------------------------------

## 1. 目标

让现有导航系统能够把 ExtraJump 当作一种真正可规划、可执行的运动能力：

-   普通跳跃不足以抵达时，能够组合使用普通跳跃和 ExtraJump；
-   能根据当前运动状态选择额外跳跃的使用时机；
-   能确认游戏是否真正触发了额外跳跃；
-   能根据实际运动结果处理预测偏差、碰撞和落脚变化；
-   不因一次跳跃失败或一次局部搜索失败，就直接认定目标不可达。

ExtraJump
也可以在自然有益时改善移动过程，但本阶段不以极限提速或专项速度排名为主要目标。

## 2. 已有基础与当前差距

Phase 4.1 已经通过 `MovementSnapshot` 和 `NativeMovementReader`
动态采集：

-   `ExtraJumpLoader.OrderedJumps` 中的注册能力；
-   每项能力的 `FullName`、注册顺序、`Enabled`、`Available`、`Active`；
-   `Player.blockExtraJumps`。

4.2 应复用这套采集，不重新建立装备名称或物品 ID 数据库。

当前导航仍然拒绝 `PotentialExtraJump` 和 `ActiveExtraJump`。现有
`PhysicsState`、`PhysicsSimulator` 只表达普通跳跃；`StateSpacePlanner`
生成的跳跃候选也没有空中再次触发 ExtraJump
的状态转换。因此，发现能力尚未转化为实际导航能力。

现有 `LocalMotionController`
已能逐帧执行输入并比较预测与实际状态；`NavigationTask`
已有落脚确认、失败记忆、安全恢复和重新规划机制，应优先复用。

## 3. 参考实现与原生机制

### 3.1 TerraBot 中值得借鉴的部分

压缩包中的实际代码表明：

-   `BotNavigation.TryClassifyJump` 会把 ExtraJump
    纳入候选跳跃边，并据此扩大地形搜索范围。
-   `BotBrain`
    在特定越障/跨沟辅助过程中，观察到角色进入下降阶段后，尝试通过
    `releaseJump = true`、`controlJump = true`
    触发原生额外跳跃，并用每次辅助状态避免重复触发。
-   `BotReachabilitySearch.Observe` 把 ExtraJump
    可用状态纳入搜索状态键；其输入序列由 `BotMovementBenchmark`
    的重放路径通过原生 `Player.Update()` 执行和观察。

这些实现提供了候选生成、触发时机和真实状态反馈方面的参考，但没有构成通用的
ExtraJump 轨迹预测模型。`BotNavigation`
中的距离和高度范围是启发式限制，不应直接作为本项目的物理常量。`BotMovementBenchmark`
也没有独立的 ExtraJump 专项基准结果，不能据此宣称 ExtraJump
已证明能提升固定比例的移动速度。

### 3.2 tModLoader 原生行为

核对的关键机制：

-   `ExtraJumpLoader.ProcessJumps()` 按 `OrderedJumps`
    顺序查找第一个满足 `Available`、`CanStart(player)` 和
    `PlayerLoader.CanStartExtraJump(...)` 的能力。
-   `PerformJump()` 设置垂直速度和 `player.jump` 持续计数，然后调用
    `OnStarted` 及对应 ModPlayer 扩展钩子。
-   `ExtraJumpLoader.UpdateHorizontalSpeeds()` 会在能力处于 `Active`
    时执行，可能改变本帧有效水平加速度和速度参数。
-   `OnStarted()` 可以重新设置
    `Available = true`，因此可重复使用的能力可能同时处于
    `Available = true`、`Active = true`。

所以，导航输入只能请求游戏尝试触发
ExtraJump；实际选择由原生注册顺序和原生条件决定。执行后必须观察哪个能力真正进入
`Active`，不能仅凭按键输入或 `Available` 的变化就认定触发成功。

能力观察和规划不得为了探测状态而额外调用
`AnyExtraJumpUsable()`、`CanStart()`、`PlayerLoader.CanStartExtraJump()`
或其他 Mod 扩展钩子。由真实 `Player.Update()` 路径执行原生判断。

## 4. MVP 范围

第一版先验证一个完整闭环，不承诺一次支持所有原版及 Mod ExtraJump。

-   复用 Phase 4.1 的动态注册和状态快照。
-   首轮真实测试使用一种行为简单的原版 ExtraJump；建议以 Cloud in a
    Bottle 作为测试装备。它只是测试场景，不代表实现应建立物品 ID 映射。
-   首轮测试尽量只让一种 ExtraJump
    处于可触发状态，避免同时存在多个候选时原生优先级与预测模型不一致。
-   支持普通跳跃后，在空中再次触发一次额外跳跃，并完成安全落脚。
-   允许规划器把 ExtraJump
    用于越障、跨越间隙或调整空中运动；不要求每次导航都使用它。
-   继续使用现有导航任务、输入执行、落脚确认、失败记忆和恢复机制。
-   G1 第三方 Mod 隔离保持不变。

暂不要求支持任意 Mod 自定义 ExtraJump 行为、所有 ExtraJump
同时可用时的通用最优选择、翅膀/火箭靴组合，或每帧运行完整空中 A\* 搜索。

## 5. 运动规划与执行要求

### 5.1 预测与状态

扩展现有运动状态和模拟，使规划能够区分：

-   普通跳跃是否已经开始、是否仍在持续；
-   跳跃键是否已经释放，是否满足再次按下的输入边沿；
-   ExtraJump 是否仍可用、是否已触发、当前是否激活；
-   当前运动状态对应的有效物理参数。

搜索状态必须体现 ExtraJump
资源是否已被本段动作消耗，避免同一份资源在一条预测路线中被重复使用。

### 5.2 触发与确认

规划器应生成包含以下过程的动作序列：

**普通跳跃 → 释放跳跃键 → 空中再次按下。**

规划器根据当前路线和运动状态选择触发时机。TerraBot
在下降阶段触发可作为首轮参考，但不应将固定下降速度阈值视为所有 ExtraJump
的通用规则。

执行层通过原生输入请求触发。随后读取当前快照及实际玩家状态，确认对应
ExtraJump 是否进入 `Active`，并检查实际速度、`player.jump`
计数和有效水平物理参数。

如果没有观察到预期激活，不得继续把预测当成已经触发；应按当前真实状态继续安全动作，或进入现有恢复和重新规划流程。

### 5.3 不重复执行扩展钩子

不要在预测搜索中反复调用 ExtraJump 或 ModPlayer
虚拟钩子来询问参数。优先使用原生运行时已经产生的状态：实际激活能力、玩家速度、跳跃计数，以及现有采集时机得到的有效物理参数。

如果某种能力的运动行为无法从这些可靠数据和已验证模型中描述，就暂不让它参与规划，而不是猜测其轨迹。

### 5.4 预测偏差与恢复

预测用于选择和组织动作，真实游戏状态决定后续行动。

-   触发失败：确认能力仍未激活，不得假定资源已经成功使用。
-   发生碰撞或轨迹明显偏离：停止依赖旧预测的输入，释放控制，并使用现有安全恢复流程。
-   未落到预期平台但落在其他安全支撑处：从真实落点继续导航，不把它直接判为任务失败。
-   安全落脚并确认后：从实际位置和剩余能力状态重新规划。
-   一次局部搜索没有找到路线：结果应保持为暂时未知/当前搜索未找到，不等同于目标不可达。

MVP
不要求无条件进行空中完整搜索；但不能在已知预测失效后继续盲目执行旧动作。

## 6. Revision 与资源状态

ExtraJump 的预期使用会造成 `Available`、`Active`
状态变化，也可能改变当前有效水平物理参数。

这些由计划动作正常引起的状态转换，不应被误判为意外能力变更，导致导航任务刚触发
ExtraJump 就调用 `InvalidateMobility()` 并进入恢复。

实现应区分以下情况：

-   能力注册/启用情况或运动模型发生变化；
-   当前动作预期中的 ExtraJump 消耗、激活和结束；
-   与计划不符的资源变化或有效物理参数变化。

具体字段和代码组织由 Codex 根据现有
`MobilityTracker`、`MovementSnapshot`、`NavigationTask`
选择最小改动。关键验收结果是：预期的 ExtraJump
状态转换能够被当前动作正常消费；意外变化仍能使不再适用的规划失效。

## 7. 验收标准

### 离线与定向测试

1.  普通跳跃后释放并再次按下，模拟器能够表达一次 ExtraJump 转换。
2.  同一份 ExtraJump 资源不会在一条路线中被重复使用。
3.  `Available = true` 且 `Active = true`
    的状态不会被错误解释为"未触发"。
4.  预测执行过程中，预期的 ExtraJump 状态变化不会无故触发任务恢复。
5.  触发失败、碰撞、落点偏差和安全恢复均有定向测试。
6.  Phase 1--3 既有导航回归保持通过。

### 真实游戏测试

1.  装备一种简单的原版
    ExtraJump，完成普通跳跃与额外跳跃组合，抵达普通跳跃无法安全抵达的平台或跨越普通跳跃无法通过的间隙。
2.  确认 ExtraJump
    确实由原生机制触发，并记录触发前后能力状态和玩家运动状态。
3.  制造一次触发未成功或运动偏离情况，确认系统不会继续相信旧预测，并能安全恢复后重新规划。
4.  落到非预期但安全的平台时，能够从实际位置继续导航。
5.  落地后能力恢复时，能够在后续动作中再次利用。
6.  两个受支持 tModLoader 引擎版本均构建通过，并运行相关回归。

第三方 Mod 的实际兼容性、任意自定义 ExtraJump 运动以及图形 Host & Play
不属于本 MVP 的完成声明。

## 8. 实现边界

本文件定义目标、必要机制和验收标准，不规定具体类拆分或每个字段的实现方式。Codex
应结合 `d238728`
的现有代码选择最小改动；若实际原生行为与本文假设不符，应先核实源码/运行时表现，采用必要调整并记录原因。

**本阶段的成功标准：导航系统能主动利用 ExtraJump
完成移动，并在实际运动不符合预测时安全处理和继续寻找路线，而不是只证明某条理想轨迹可以被模拟出来。**
