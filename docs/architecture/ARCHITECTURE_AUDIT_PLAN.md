# 架构审查计划

**工作文档 · 非规范性**

本文组织对当前 Agent 架构的审查。它不是当前架构说明、缺陷清单或已批准的重构计划；实现事实以审查时的源码为准，验证结论必须注明实际测试等级。

## 审查目标

判断现有系统能否让 Agent 稳定完成连续 Terraria 游戏目标，以及失败是否能被正确定位、解释和恢复。重点不是增加 API 数量，而是明确高层决策、程序编排、游戏任务和原生执行之间的责任边界。

## 审查范围

1. **Agent Loop 与上下文**：聊天轮次、事件、工具选择、历史投影、中断、等待和最终回复。
2. **Lua Runtime 与原子 API**：程序生成成本、API 可组合性、Schema、返回值、错误传播、预算和取消。
3. **Task Runtime 与身体控制**：任务受理/终态、导航、直接输入、挖掘、局部恢复、输入释放和 unknown。
4. **Perception 与 Navigation**：观察范围/时效/未知状态、语义对象、物理模型、局部规划、执行偏差和落脚确认。
5. **Evaluation 与 Observability**：定向测试、隔离原生场景、Host & Play、真实模型任务、失败分类和可复现性。

## 比较的问题

审查至少比较三种交互方向，不预设结论：

- **直接 Tool Calling**：简单、结构化，但多步骤行为可能需要更多模型往返。
- **Lua 单一入口**：可组合、减少往返，但模型需要生成正确程序，运行时失败边界更复杂。
- **混合方式**：简单操作与复杂程序分流，但需要清晰的接口职责，避免两套策略重复。

参考 Numen 时追踪设计动机、演变、测试与撤销记录，不只复制当前实现。Minecraft 与 Terraria 的游戏规则、Player 生命周期和网络权威不同，必须单独验证适配价值。

## 分析方法

每个问题按以下结构记录：

- **事实**：源码、协议或测试直接证明的行为。
- **推断**：由实现推导、尚未验证的风险。
- **问题**：真实任务中观察到的失败及可复现条件。
- **选项**：可能的局部修复或架构调整及其代价。
- **验证**：能够区分方案效果的最小测试/游戏场景。

区分游戏规则、策略限制和运行时安全保障。Actor/World/Generation 身份、控制权、取消、输入释放、截止时间和 unknown 隔离不得仅为提高成功率而删除。

## 交付结果

审查应产出当前调用链与职责图、已证实问题及证据、待验证假设、方案比较和优先级建议。只有经讨论确认的设计才进入正式架构文档；实现后的行为和参数更新到对应专题文档。

本文件不规定重构顺序，不授权代码变更，也不把单次成功或失败提升为普遍结论。
