# Exploration V2 设计与验收方案

## 1. 目标

将现有固定四方向的短程探索改造为基于空间目标、访问历史和实际导航结果的持续自主探索。Agent 应能在陌生的 Terraria 世界中沿自然地形深入，发现新空间和资源，遇到死路或不便通行的地形时尝试其他目标，并在调查资源后继续探索。

LLM 负责游戏阶段、生物群系、资源需求等宏观目标以及重要发现的处理；探索程序负责普通选路；Navigation 负责抵达目标，包括其已经支持的挖掘、搭建、绳索等地形改造与移动操作。

不要求完整遍历世界、预测未知通道的资源价值或保证原路返回。

## 2. 现有基础与实现边界

设计基于此前分析的 `codex/exploration-field-results` 提交 `3402459ad8ab850865c99239512b8228776b3250`。开发前核对实际工作分支及其与该基准的差异，以当前源码为准。

- `AiMap`：持久化已观察地形，已有分块和地图版本机制；近期脚部足迹目前不随世界持久化。
- `ScenePassages` / `observe_scene`：提供局部身体空间连通性、通道提示、落脚区域和观察覆盖信息。
- `python/directional_explorer.py`：按四方向挑选目标并执行短程导航；当前预算为 6 段、单段 12 秒、整趟 45 秒。
- `navigate_to` 与现有任务运行时：负责实际导航、地形改造、进展判断、任务终态和输入释放；复用已有自卫、换气等暂停恢复机制。
- `ResourceHistory`、自主模式、Lua 与 MCP：复用已有资源观察、发现去重和工具调用设施。

本次不引入 BFS 距离带、骨架提取、完整洞穴拓扑图或独立动态可达性模型。优先验证简单方案；仅根据测试暴露的具体问题增加复杂度。

## 3. 空间候选生成

探索的基本单位是世界坐标下的待调查位置或小区域，而不是方向或整条洞穴。

候选来源：

1. 当前观察及已知地图中尚未实际访问的落脚位置或开放空间（Visit Frontier）。
2. 已知开放空间与真实未知地图之间的边界（Map Frontier），以能进一步观察该边界的位置作为调查目标。
3. `ScenePassages` 提供的自然通道、出口和落脚提示。

将相邻且属于同一局部空间的候选适度合并；保留薄墙隔开的不同目标。候选应覆盖多个方向，不以当前朝向上的正位移作为必要条件。采用有界局部/区域查询，并在局部候选耗尽时查询已保存的目标及更广的已知地图。不得将观察窗口外侧、采样不足或仅被实心墙隔开的未知 Tile 无条件视为自然通道。

Flood Fill 只提供自然几何连通性的优先级信息：连通不保证运动可达，不连通或连通性未知也不排除候选。利用已有落脚区域提高目标的可执行性。缺少安全落点但存在值得调查的开放空间时，先生成已知入口或观察站位；不要把任意空中坐标直接当作 `navigate_to` 的安全落地目标。实际可达性由 Navigation 验证。

## 4. 探索记忆与选路

### 4.1 持久访问记录

在现有 AiMap 基础上增加独立的实际访问标记（VisitMap，建议使用分块位图或等价轻量表示），按世界和角色隔离持久化。记录实际采样的角色脚部位置；不将观察、照亮或挖开空间视为访问，不为瞬移补画中间轨迹。继续利用已有近期足迹判断实际进入和循环行为。

### 4.2 探索目标记录

每个目标至少记录：稳定标识、类型、世界坐标锚点/调查范围、可执行的导航目标、状态、尝试记录及必要的观察版本。可选保存发现顺序与来源，支持深度优先式选路。

目标去重基于世界坐标及局部空间关系，不依赖临时场景 ID 或滚动窗口原点；不仅凭距离合并隔墙目标。不同窗口重复发现同一目标不得不断生成新记录。保存待探索、活动、已调查、暂缓等状态；地形变化后可重新验证。访问某个目标不代表整个洞穴已完成调查。

### 4.3 选路策略

保持简单的深度优先倾向，不实现严格 DFS 图遍历。

- 保持正在产生进展的活动目标。
- 从可用的未调查候选中优先选择自然几何连通、已有落脚点且靠近当前探索路线的目标。
- 当前局部延伸受阻或耗尽时，考虑先前保存的支路与其他 Frontier；不要求沿原路返回。
- 不连通的已知开放空间仍是有效候选，可交给导航尝试改造地形后抵达。历史失败目标进入暂缓集合，避免抢占尚未尝试的候选。
- 同类候选采用简单的发现顺序、距离等稳定规则打破平局。不需要预测资源收益或计算复杂综合评分。

失败记录绑定目标及尝试上下文，而不是方向或全局地图版本。无进展、已知失败或搜索预算耗尽后避免立即重复尝试；有相关地形变化、不同合理接近位置或经过适当冷却时允许重试，并设置有限的重复尝试机制。普通行走导致观察窗口移动，不应自动清空失败记录。

重复经过旧路线可以是有效导航的一部分。循环检测以目标调查证据、实际访问新增、目标相关观察与任务进展为依据；单纯坐标变化或无关地图变化不能无限刷新无进展预算。

## 5. 持续探索控制器

在现有共享探索实现上重构控制器，使自主模式、Lua、MCP 使用相同的选路与状态管理逻辑。每轮执行：

`观察 → 更新候选及历史 → 选择目标 → 提交/跟踪 Navigation → 核验结果 → 更新状态与发现 → 继续`

推荐由 C# 侧负责地形、访问记录及空间候选提取，Python Host 负责探索目标集合、策略、任务生命周期和资源发现。具体模块拆分由 Codex 根据当前架构确定。

### 5.1 导航契约

- 使用现有 `navigate_to` 和任务所有权/回执机制。一次只拥有一个活动导航任务，导航负责移动及实际支持的地形改造。
- 不以 X/Y 正向位移判断探索是否成功。Visit Frontier 的完成需要真实访问证据；Map Frontier 的完成需要目标相关的新观察或重新验证后确认其已被揭示。单纯抵达入口、无关位移或导航回执成功不足以证明整个调查目标完成。
- 导航已确认失败时记录目标并重新选路；观察不完整、搜索预算耗尽和安全中断不能直接当作永久不可达。
- 战斗、换气等原生反射暂停时保留活动目标及任务身份。只有在原任务终态及输入释放得到确认后才交接或派发下一身体任务；不确定时沿用现有安全停止机制。

### 5.2 执行预算与会话

取消四方向探索对单段 12 秒、最多 6 段的固定硬限制，复用 Navigation 自身的执行及进展保护。45 秒可作为初始阶段性检查预算，不应仅因时间达到而取消仍有有效进展的导航。

到达软预算时停止启动新的探索段，并在既有所有权机制下安全完成/交接当前任务。若现有任务协议支持可靠的跨调用继续跟踪，也可返回运行状态及同一任务身份；不得产生无人跟踪的身体任务。保留有限的无进展、观测和执行保护，不能无限等待。

活动目标、待探索集合、失败历史与资源调查上下文在探索调用之间保留。用户中断、调查资源、回城或重启后重新观察并验证状态；不盲目恢复失效任务 ID。长期访问记录和待探索目标应可恢复，临时执行授权不得持久化为有效授权。

### 5.3 LLM 接口

保持统一 `explore` 能力。支持不指定方向的自然探索；既有方向参数可保留为宏观偏好或兼容入口，不再限制每段实际移动。允许继续已有探索会话及指定资源发现条件（沿用 `seek` 语义）。根据当前调用契约确定最小必要的接口调整，同步更新自主模式、Lua、MCP 的工具说明。

普通岔路、可处理障碍和短暂反射不需要 LLM 决策。命中指定发现、阶段性检查、需要宏观决策、无合适候选或安全中断时返回清晰结果。复用 ResourceHistory 对发现去重。返回信息应包含实际位置、探索进展、相关发现、停止/暂停原因及必要的任务回执。

## 6. 实现与验证顺序

按以下顺序完成，每阶段通过定向测试后再进入下一阶段。

| 阶段 | 内容 | 验收重点 |
| --- | --- | --- |
| 1 | VisitMap、候选生成与 Flood Fill 优先级 | 两类 Frontier、真实访问与观察分离、隔墙候选保留、同一目标去重 |
| 2 | 目标状态、选路及失败/循环管理 | 弯曲路径、死路换路、跨调用状态、有限重试、地形变化后重新验证 |
| 3 | 集成共享控制器、导航任务及 LLM 接口 | 实际抵达、任务所有权和释放、反射恢复、资源调查后续接、软预算 |
| 4 | 原生场景与自然世界对照测试 | 证明真实游戏行为，而非只验证目标选择或新增地图数量 |

优先复用现有 C# 场景与 AiMap 测试、Python 探索测试、原生专服导航夹具及自然世界测试设施；先静态检查和编译，再运行定向测试、原生验证与相关回归。测试失败需保留原因及回执。

### 6.1 可控场景验收

| 场景 | 预期行为 |
| --- | --- |
| S/U 形通道 | 实际继续深入，不因方向反转而停止 |
| Y 形及同方向双支路 | 进入其中一支后保留另一支；死路后能够选中并实际进入其他支路 |
| 隔薄墙的平行空间 | 不错误合并访问/失败记录；不连通目标仍可成为后备候选 |
| 自然连通与需改造两个候选 | 可比条件下优先自然连通候选；自然候选耗尽后仍可尝试改造抵达 |
| 环路、开放洞穴及死路 | 避免无进展循环；无明确岔路也能选取新空间 |
| 导航失败与采样不足 | 有界重试并改选目标；不错误标记已访问、永久不可达或探索完成 |
| 观察、实际移动、瞬移与重启 | 访问记录准确且隔离持久化；重启后可恢复候选并重新验证 |
| 战斗/换气、人工中断、阶段预算 | 正确暂停或停止并恢复/交接；无重复身体任务及未确认释放 |
| 资源调查后继续 | 保留此前的活动目标或剩余候选，避免从头重复探索 |

### 6.2 自然世界验收

建议至少使用两个自然生成世界（优先复用已有开荒测试种子），在相同起点、初始装备、观察权限及测试时间下对比现有方向探索与 V2。区分确定性控制器测试和自由 LLM 测试：前者证明探索算法，后者证明完整自主游戏循环。每个世界建议持续 5–10 分钟；若遇到无法继续的环境或任务安全退出，记录真实原因，不以伪造位置或关闭危险来替代验收。可以在受控算法测试中使用固定宏观目标和夹具，但自然世界最终验证应保留正常游戏环境。

核心证据：真实位置轨迹、目标选择/完成记录、支路进入与资源发现/调查、导航回执、输入释放状态，以及中断后恢复情况。辅助统计新访问位置、重复移动、地图新增、导航失败和 LLM 调用次数。指标用于对比与诊断，不作为游戏内价值优化目标。

自然世界验收关注能否稳定深入、遇阻换路及恢复探索。不要求每个种子一定出现宝箱或特定资源；没有实际到达其他支路的运行不能作为支路探索成功的证据。记录新旧算法的真实差异、未通过场景和现有导航能力的实际瓶颈，不将单次幸运结果当作普遍能力。

## 7. 交付

提交实现、更新的接口/架构文档、自动测试和原生/自然世界验证报告。报告应明确测试环境、种子与装备、实际结果、相关回执或轨迹、失败与未验证项。保留独立开发分支，便于与基线对照和评审。

本设计为待验证的第一版：候选聚合尺度、优先级平局规则、冷却及预算的具体值由实现和测试确定；若存在现有 Navigation 不支持的目标类型，先据实报告，按最小必要范围修正接口或候选策略，而不是推定所有空间均可达。
