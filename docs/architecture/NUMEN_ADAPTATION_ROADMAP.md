# Numen 架构研究与 Terraria 适配选项

**状态：** 参考方案草案；各模块是否采纳须经独立审查和验证\
**项目：** Terraria AI Companion\
**参考项目：**
[Dwinovo/minecraft-numen](https://github.com/Dwinovo/minecraft-numen/tree/1.21.1)

 > 本文列出一种研究框架，不是已批准的目标架构或排期。它与 `ARCHITECTURE_AUDIT_PLAN.md` 一样，不覆盖正式架构和专题契约。

## 1. 项目目标

Terraria AI Companion 的长期目标，是让 AI 成为 Terraria
世界中的第二名玩家，能够像真人一样理解环境、探索世界、采集资源、挖掘、建造、合成、战斗和生存。

目前项目已经实现了 Python Agent、Lua 编排、TCP IPC、C# tModLoader
游戏适配，以及部分原子操作、环境感知、导航和执行验证机制。

但现阶段仍存在一个明显问题：底层操作能力不断增加，Agent
却尚未形成足够完整、稳定的游戏行为能力。

因此，后续开发不再以单独增加 API 为主要目标，而是参考 Numen
已经形成的系统设计，将 Agent 拆分为职责明确、相互协作的模块，逐个完成
Terraria 适配。

核心目标：

**学习 Numen 的成熟架构与设计思想，而不是简单复制它的 API。将其适合
Terraria 的机制转化为我们自己的系统能力。**

## 2. 总体架构

将 Numen 的整体设计归纳为九个逻辑模块：

  ------------------------------------------------------------------------------------
  模块                                核心职责
  ----------------------------------- ------------------------------------------------
  1\. Agent Brain                     意图理解、上下文组装、决策循环、事件驱动

  2\. Program Runtime                 Lua 程序执行、沙箱、预算、中断、程序组合

  3\. Atomic API & Capability         原子接口、能力注册、参数契约、错误语义

  4\. Perception                      世界感知、语义对象、环境信息

  5\. Spatial & Navigation            空间模型、寻路、移动、站位与到达判定

  6\. Task Runtime                    长时间任务的受理、执行、进度、中断、恢复与结束

  7\. Behavior Modules                探索、挖掘、建造、战斗、合成等可复用行为

  8\. Reflex & Safety                 自主生存、本能反应、危险处理、权限与安全

  9\. Persistence & Observability     记忆、世界知识、事件、动作记录与持久化
  ------------------------------------------------------------------------------------

这些是逻辑职责划分，不要求每个模块都成为独立项目或程序集。

模块之间允许存在调用与数据依赖，但必须明确职责边界，避免同一套机制在多个模块中重复实现。

### 2.1 核心数据流

整体采用持续闭环：

**感知 → 决策 → 规划 → 执行 → 验证 → 再感知**

-   Agent Brain 理解目标并决定下一步。
-   Perception 提供结构化环境信息。
-   Spatial & Navigation 提供空间判断和移动能力。
-   Program Runtime 组织多个原子操作。
-   Task Runtime 管理持续执行的任务。
-   Behavior Modules 提供可复用的游戏行为。
-   Reflex & Safety 处理需要优先响应的危险。
-   Persistence & Observability
    记录实际发生的事情，并为后续决策提供依据。

LLM
负责高层目标理解和决策，不负责每帧的身体控制、精确碰撞计算和底层执行细节。

### 2.2 与 Numen 五层操作体系的关系

Numen 还采用了一套五层操作体系：

  层级   Numen              Terraria 对应方向
  ------ ------------------ ------------------------------------
  ⓪      Body Control       原生输入、物理、移动与底层控制
  ①      Atomic API         原子游戏操作及统一接口契约
  ②      Built-in Modules   随模组提供的 Lua 行为模块
  ③      User Modules       用户自定义及可修改的 Lua 模块
  ④      Current Program    当前由 Agent 生成和执行的 Lua 程序

五层体系描述的是程序如何操作游戏，而九个模块描述的是整个 Agent
系统如何分工。

两者是不同维度的架构划分，并不冲突。

## 3. 九个模块的适配目标

### 3.1 Agent Brain

负责 Agent 的认知与决策循环。

主要职责：

-   接收用户指令和游戏事件。
-   维护对话历史和当前上下文。
-   组装系统提示词、运行时状态和工具定义。
-   管理模型请求与工具调用。
-   处理插话、中断、死亡及失败。
-   维护长期目标，并根据任务结果继续决策。

适配目标：

检查现有 Python Agent
Loop、Prompt、上下文管理、事件处理与工具调用之间的职责边界。

重点研究 Numen 的事件队列、事件投递、上下文组装和循环中断机制。

不以重写现有 Agent Loop 为预设目标。

### 3.2 Program Runtime

负责模型生成程序的执行与编排。

主要职责：

-   Lua 沙箱与程序执行。
-   原子 API 调用。
-   执行预算和资源限制。
-   程序中断与错误处理。
-   程序输出和结构化结果收集。
-   内置模块与用户自定义模块。

适配目标：

完善现有 Lua 运行时，使 Agent
能够通过一段程序连续组合多个操作，而不必每完成一个小动作就重新请求 LLM。

需要明确程序执行与后台游戏任务的区别：Lua 是编排环境，Task Runtime
负责持续任务的生命周期。

### 3.3 Atomic API & Capability

负责 Agent 与游戏能力之间的接口契约。

主要职责：

-   原子 API 注册与分发。
-   参数和返回值定义。
-   统一数据类型。
-   结构化错误语义。
-   能力描述和帮助信息。
-   运行时能力与模型可见能力的一致性。

适配目标：

让接口具有稳定、清晰、可组合的契约。

重点研究 Numen 的 API 登记机制、类型系统、帮助生成及错误处理。

避免模型通过猜测参数、猜测返回值或重新拼接坐标来完成接口调用。

### 3.4 Perception

负责将 Terraria 世界转换为 Agent 可以理解和使用的结构化信息。

主要职责：

-   玩家状态和身体状态。
-   局部地形感知。
-   Tile 与环境对象识别。
-   实体和敌人识别。
-   掉落物、矿物、火把、工作站等对象识别。
-   未知区域、观察范围和信息时效管理。

适配目标：

从当前 `observe_scene`、`scan_tiles`、`scan_entities`
等接口出发，研究并建立统一的语义对象模型。

重点研究 Numen 的 Position、Block、Entity、Item、Cluster、Window
等数据类型，以及它们如何被扫描接口返回、如何被行为接口消费。

核心要求：

**观察到的对象应当能够直接传递给相应操作接口，而不是要求 LLM
再次根据地图计算坐标。**

### 3.5 Spatial & Navigation

负责统一的空间模型与导航系统。

主要职责：

-   Tile 几何和碰撞判定。
-   玩家身体模型和运动学。
-   可站立位置与有效交互范围。
-   路径搜索。
-   移动执行。
-   动态障碍处理。
-   重规划与到达判定。

适配目标：

参考 Numen 寻路系统的分层设计，检查现有移动、跳跃、落地、导航与 Direct
Input 实现。

重点是统一空间判据。

移动、挖掘、放置、攻击和交互不应该各自维护相互矛盾的距离与可达性判断。

### 3.6 Task Runtime

负责持续游戏任务的完整生命周期。

主要职责：

-   任务请求与参数验证。
-   任务准备与可执行性检查。
-   任务受理。
-   任务执行与进度管理。
-   任务替换和取消。
-   中断与失败处理。
-   完成事件和结构化回执。

适配目标：

参考 Numen 的 Task Dispatch、Preparation、Task Slot 和 Task Finished
机制，逐步建立统一的任务运行时。

移动、挖掘、建造、战斗和收集等长时间行为应当使用一致的任务管理机制。

需要明确：

-   任务真正可以开始后才返回受理成功。
-   受理前失败不应产生虚假的任务记录。
-   长时间任务需要可查询的状态和进度。
-   任务结束应主动产生结果事件，不依赖 LLM 高频轮询。
-   中断后应根据当前世界状态重新判断，而不是盲目恢复过期坐标或路线。
-   任务失败必须保留可供上层决策使用的原因。

### 3.7 Behavior Modules

负责把原子操作组合为完整、可复用的游戏行为。

主要方向：

-   Exploration：探索、下矿洞、返回安全区域。
-   Mining：寻找矿物、移动、挖掘、拾取。
-   Building：建造庇护所、铺设平台、放置火把。
-   Combat：攻击、追踪、躲避和防御。
-   Inventory：整理背包、穿戴、切换物品。
-   Crafting：选择配方、寻找工作站、准备材料和合成。

适配目标：

建立随模组提供、可由用户修改和复用的 Lua 行为模块。

行为模块负责组织流程，不重复实现底层物理、权限、任务生命周期和空间判据。

### 3.8 Reflex & Safety

负责不依赖 LLM 实时思考的底层反应机制。

主要方向：

-   坠落处理。
-   溺水和窒息处理。
-   危险地形规避。
-   低生命值生存反应。
-   脱困。
-   战斗防御和必要时撤退。
-   权限与危险操作限制。

适配目标：

研究 Numen 的 Reflex 登记与身体控制优先级机制。

本能应当能够在必要时抢占普通行为的控制权，并在处理完成后交还控制权。

本能不是普通 Lua 行为模块，也不应该要求 LLM 每次危险发生时重新判断。

### 3.9 Persistence & Observability

负责长期状态、执行证据和系统可观测性。

主要方向：

-   对话历史。
-   长期记忆。
-   当前目标与任务状态。
-   世界知识和探索记录。
-   实际动作历史。
-   事件日志。
-   任务完成和失败记录。
-   角色持久化。

适配目标：

在现有事件日志、动作结果历史和自动地图累积机制的基础上，逐步明确不同数据的职责与持久化边界。

特别区分：

-   Memory：长期经验和需要记住的信息。
-   WorldKnowledge：探索过程中积累的世界知识。
-   CurrentTask：当前任务状态。
-   ActionHistory：实际发生的动作与结果。
-   EventJournal：系统事件及其发生顺序。

可观测性是所有模块的基础要求，不应等到最后才补充日志。

## 4. 模块适配路线

采用逐个模块研究、审查、设计、实现和验收的方式推进。

### 阶段 0：现有基础审查

梳理现有 Python Agent、Lua Runtime、TCP IPC、C#
游戏适配层、原子操作、导航、感知和日志体系。

明确已有实现与九个模块的对应关系，识别重复职责和缺失接口。

不预设重写现有架构。

### 阶段 1：Perception + Object Model

优先完善环境感知和语义对象体系。

验收方向：

-   能识别有意义的地形与环境对象。
-   能区分未知区域和已知区域。
-   对象具有统一的数据结构。
-   感知结果可以直接传递给操作接口。
-   不需要模型自行拼接坐标和对象信息。

### 阶段 2：Spatial & Navigation

完善统一空间模型与导航系统。

验收方向：

-   连续移动、跳跃和下落。
-   处理平台、斜坡、坑洞和障碍。
-   识别可站立位置和交互范围。
-   导航失败具有明确原因。
-   能够在环境变化后重新规划。

### 阶段 3：Task Runtime

建立统一的持续任务管理机制。

验收方向：

-   多种长时间操作共享任务生命周期。
-   任务受理和执行状态明确。
-   支持进度、取消、中断和完成。
-   任务结果主动反馈。
-   能够根据最新世界状态重新判断任务。

### 阶段 4：Atomic API + Program Runtime

完善原子接口契约与 Lua 程序运行机制。

验收方向：

-   API 参数和返回值明确。
-   错误语义统一。
-   能力描述与实际实现一致。
-   Lua 可以组合多个操作。
-   程序能够正确处理任务等待、中断和失败。

### 阶段 5：Behavior Modules

逐步实现完整游戏行为。

建议优先探索与采集，再扩展建造、库存、合成和战斗。

验收方向：

Agent
能够使用可复用模块完成跨越多个原子操作的游戏目标，而不是只完成单次动作。

### 阶段 6：Reflex & Safety

完善自主生存、本能响应和控制权管理。

验收方向：

常见危险不需要依赖 LLM
每次重新思考；本能能够及时响应并正确处理中断和控制权交接。

### 阶段 7：Agent Brain + Persistence 集成完善

在前述模块逐渐稳定后，进一步完善整体认知循环、事件驱动、长期目标、记忆与恢复机制。

验收方向：

Agent
能够持续理解自身状态、当前目标和执行结果，并根据真实世界变化调整决策。

说明：Agent Brain
与持久化、可观测性从项目初期就持续维护。本阶段指整体集成和完善，不意味着前期不开发这些能力。

## 5. 统一开发方法

每个模块均采用以下流程：

1.  **Numen
    源码研究**：理解对应模块的实际实现、职责边界、数据结构和设计取舍。
2.  **Terraria 现状审查**：检查现有代码，确认哪些能力已经存在。
3.  **差距分析**：区分可直接借鉴的设计和需要适配 Terraria 的部分。
4.  **模块设计**：明确职责、接口、依赖、数据流和验收标准。
5.  **定向实现**：围绕当前模块完成必要改造。
6.  **分层测试**：进行离线测试、原生场景测试和 Lua/IPC 测试。
7.  **实机验收**：验证 Agent 是否真正获得预期游戏能力。
8.  **文档归档**：记录实现、设计差异、测试证据和剩余问题。

每个模块完成后，应更新本路线文档中的适配状态，并维护对应的详细设计文档。

## 6. 设计原则

1.  **借鉴成熟实现，而非重复发明。** 优先研究 Numen 已经验证的设计，结合
    Terraria 的机制进行适配。
2.  **以职责划分模块，而不是以 API 数量划分。**
3.  **不重复造轮子。** 已有实现先审查，再决定复用、改造或替换。
4.  **统一事实来源。**
    空间、对象、任务状态和动作结果应有明确的数据来源。
5.  **原子操作负责执行，行为模块负责组合。**
6.  **程序运行时与任务运行时职责分离。**
7.  **高频控制留在游戏运行时，LLM 负责高层决策。**
8.  **执行结果必须真实、可验证、可追踪。**
9.  **允许失败，但必须保留失败原因和必要的恢复依据。**
10. **以真实游戏行为作为最终验收标准，而不是 API 数量或离线测试数量。**
