# Terraria AI Companion：统一导航系统设计与实现

## 目标

实现一个由游戏侧自主执行的通用导航任务。Agent
只提供目的地；导航系统自行决定如何抵达，包括行走、跳跃、下落，以及必要的挖掘开路和放置通路。

Agent 不负责判断障碍、选择挖掘位置、调用挖掘工具或编排导航步骤。

本次工作聚焦于把现有导航与地形改造能力整合为统一
Navigation，不扩展战斗、寻矿、拾取等其他功能。

Player 输入控制或原生工具执行机制。

## 目标职责

``` text
Agent: navigate_to(x, y)
          |
          v
Navigation Task / Controller
          |
          +--> Planner
          |      |
          |      +--> Walk / Jump / Drop
          |      +--> Dig clearance / tunnel / descent
          |      +--> Place platform / support
          |
          +--> 现有移动执行器
          +--> 现有挖掘执行器
          +--> 现有放置执行器
```

-   **Planner**：读取玩家与地形状态，搜索可执行路径，决定移动或地形改造。规划阶段不得直接修改世界或控制玩家。
-   **Navigation
    Controller**：持有整个导航任务，串行派发子动作，观察执行结果，并决定继续、重规划或结束。
-   **Movement Executor**：执行移动输入并核验实际位置。
-   **Mining / Placement
    Executor**：只执行指定的原生挖掘或放置动作并返回可验证结果，不自行规划导航路线。

所有身体动作必须由同一个根 Action 串行管理。

## 规划模型

### 目标与到达

对 Agent 暴露单一目的地接口
`navigate_to(x, y)`。目标应表示玩家身体可占据的位置，而非要求玩家中心精确落在
Tile 中心。

到达必须根据真实玩家位置、碰撞箱及必要的稳定落脚状态验证。搜索距离足够近不等于任务完成。

### 世界与运动状态

沿用项目现有连续物理状态与 Terraria
原生碰撞判定。规划节点至少要区分足以影响后继动作的玩家位置、速度、落脚/空中状态；不能仅以
Tile 坐标作为状态，否则不同速度或运动状态可能被错误合并。

地形可通行性应基于实际碰撞、支撑和身体净空。半砖、斜坡、平台、家具、Actuated
Tile、液体及危险地形不能统一按简单的 `hasTile` 判断。

规划与执行必须共享同一套地形/碰撞事实来源。未知地形不得默认视为安全。

### 通行边

先实现当前物理与执行器能够可靠支持的边：

-   水平行走
-   跳跃
-   安全下落
-   必要的地面高度变化
-   挖掘身体净空
-   挖掘通道
-   挖掘脚下支撑并等待实际下落
-   放置平台或支撑

绳索、钩爪、飞行、坐骑等作为后续扩展，不作为本次首要验收范围。

每种边都要定义起始条件、预计落点、地形前置条件、改造内容、成本及执行后的验证条件。

### 地形改造模拟

参考 Numen 的
`Draft`：规划器在搜索视图中模拟挖掘和放置后的地形，不直接修改 Terraria
世界。

模拟至少要能反映：

-   被挖 Tile 的碰撞与支撑变化
-   玩家身体净空是否足够
-   放置后是否形成有效落脚面
-   支撑移除后是否存在可验证的安全落点
-   液体、危险地形或其他已知环境风险

不能只按挖掘格数选择路线；应比较绕行、跳跃、挖掘和放置的综合成本。

### 成本与能力

成本考虑移动时间、跳跃/下落、挖掘时间、放置时间、资源消耗及可识别的危险。

分别判断：

1.  该类地形改造是否允许；
2.  玩家是否具有适用工具或材料；
3.  目标格是否能被原生机制修改；
4.  修改后是否安全且可通行。

不能把这些条件折叠成一个布尔值，也不能用静态方块白名单替代原生能力判断。

## 执行闭环

``` text
读取玩家与局部地形
        |
        v
搜索路线 / 选择下一条边
        |
        v
派发移动、挖掘或放置子动作
        |
        v
等待子动作终态
        |
        v
核验真实位置与世界变化
        |
        +-- 符合预期：继续路线
        |
        +-- 世界/位置变化：重新规划
        |
        +-- 失败或状态不明：停止并返回准确结果
```

路线是基于当前世界状态的计划，不是不可变的执行脚本。每次地形改造后必须重新观察；移动落点与预测不一致时不得盲目执行旧路线。

预算耗尽、预测不一致、取消和 `unknown` 必须与"已证明无路"区分。`unknown`
后不得盲目重放动作。

## 失败记忆与搜索预算

参考 TerraBot 的失败路线记忆及 Numen 的有界搜索/路线续接：

-   搜索必须有明确节点预算及时间预算。
-   可返回经过验证的部分路线，但必须标明尚未到达目标。
-   预算耗尽不能报告为不可达。
-   只记忆已经实际执行并确认失败的边；预测阶段拒绝不等同于执行失败。
-   失败记忆绑定 World Session、Actor Generation
    和相关地形状态；世界或能力变化后应允许重新尝试。
-   若实现路线续接，必须保证接续结果确定后再进入需要等待的路线尾段；第一版可先采用分段重规划，避免为提前规划引入不必要复杂度。

`NativeMiningOpening`

后续只负责确定目标、调用通用导航到达有效挖掘位置，再调用挖掘执行器并核验目标破坏；不得保留第二套独立开路导航算法。

## 实施顺序

1.  **梳理现状**：确认导航、挖掘、放置、任务运行时的调用链；对照 Numen
    和 TerraBot，给出可复用代码映射及必要改动点。
2.  **统一规划**：建立面向二维目标的统一路径状态与移动边，优先复用现有物理模拟和碰撞适配。
3.  **纳入地形改造**：把挖掘和放置作为规划边；复用原生执行器，规划阶段只模拟，执行阶段核验。
4.  **闭环执行**：串行执行子动作，执行后观察并重规划；补充失败记忆与预算边界。
5.  **整合工具**：提供 `navigate_to`，让 `mine_target` 复用通用导航。

先完成现状梳理再实现；若代码现状与文档假设不符，以仓库实际实现为准，并在交付说明中指出差异。

## 验收标准

-   平地目标可达，且到达状态经过真实位置/落脚验证。
-   能自主选择行走、跳跃和安全下落。
-   普通实心阻挡存在时，能自主规划并挖掘开路。
-   需要向下抵达时，能挖除支撑、等待 Terraria 实际下落并重新规划。
-   缺少落脚支撑时，在有合适材料且安全的情况下能规划、放置平台并验证。
-   能比较绕行与地形改造路线，而非固定优先某一种方式。
-   地形改造或移动结果与预测不一致时会重新规划，不盲目续行。
-   搜索预算耗尽不会误报不可达；`unknown` 不会触发盲目重试。
-   移动、挖掘、放置子动作在同一根 Action
    下严格串行；取消/超时后正确释放输入。
-   `mine_target` 复用通用导航。
-   现有移动、挖掘、放置及 `mine_target`
    回归测试通过；原有自动开路隔离场景应回归，行为有意变化时提供对应替代测试。
