# Terraria 自主导航系统优化设计

**版本：0.2（精简架构稿）**\
**代码基线：** `codex/unified-autonomous-navigation`，提交
`b2447c4ea369160c2a110f4739d5db7766dda72a`\
**参考项目：** Numen `1.21.1`；用户提供的 TerraBot 源码/反汇编资料

## 1. 目标

建立一套由游戏侧自主运行的 Terraria 导航系统。

Agent 只需要提交最终目的地，例如
`navigate_to(x, y)`。导航系统负责规划路线、执行移动、根据需要改造地形、观察执行结果、处理受阻情况并持续推进，直到抵达目标或确认无法安全继续。

导航不应把内部搜索范围、单次计算预算或中间路线交接变成 Agent
需要处理的问题。一次搜索没有找到最终目的地，不代表整个导航任务失败。

## 2. 当前实现与主要问题

当前实现已经具备重要基础： -
基于玩家物理状态进行路线搜索，并复用现有物理预测和 Terraria
原生碰撞验证。 - 已有导航任务与进度管理。 -
移动、挖掘和放置能够在同一个根 Action 下串行执行。 -
已有有限的横向开路、向下开路和支撑放置能力。 - `mine_target`
已能复用共享导航能力。

目前需要重点改善的不是简单增加更多局部规则，而是导航任务的持续推进能力： -
单次搜索范围和预算较容易成为整个任务的实际能力边界。 -
部分路线、路线接续和搜索预算耗尽的语义还不够完整。 -
对搜索推断出的困难区域与实际执行失败的路线，缺少足够有效的学习和记忆。 -
移动与地形改造目前仍偏向局部候选比较，尚不能充分考虑连续行动的整体效果。 -
Terraria
的落脚面、平台、碰撞箱和特殊运动能力还需要更系统地融入导航模型。

## 3. 参考项目的借鉴方向

### Numen：导航任务如何持续推进

重点借鉴其导航任务、搜索、执行跟踪和学习之间的协作方式： -
将导航视为持续运行的行程，而不是一次性路径计算。 -
搜索可以交付可靠的部分路线，执行后继续规划下一段。 -
利用搜索学习和实际执行反馈，减少重复尝试失败路线。 -
在当前路线执行期间准备后续路线，并在交接时结合真实状态验证。 -
区分搜索预算耗尽、暂时没有路线、状态未知和确实不可达。

借鉴的是架构思想和行为，不要求照搬 Numen 的类、接口或 Minecraft
运动模型。

### TerraBot：Terraria 的运动与地形特性

重点借鉴其对 Terraria 世界的建模和导航策略： - 使用落脚面/Surface
等空间结构组织候选路线。 -
考虑角色碰撞箱、支撑面、半砖、斜坡和平台的差异。 -
将行走、跳跃、下落等运动作为不同的可行路线连接。 -
采用分阶段或多尺度搜索，避免一次搜索承担整个世界的计算量。 -
研究其路线接纳、Waypoint 跟踪、失败路线记忆和地形变化后的失效处理。 -
将空中导航等特殊运动视为独立能力，不把普通地面导航模型误当成完整运动模型。

本项目已有精细物理模拟和原生碰撞验证，应优先评估如何与上述空间结构结合，而不是为了模仿参考项目而替换现有有效能力。

## 4. 目标架构方向

导航系统应形成一个完整闭环：

1.  接收 Agent 的最终目标。
2.  根据当前玩家状态和已知地形规划可执行路线。
3.  执行路线，并持续跟踪实际进度。
4.  遇到偏差、障碍或地形变化时，结合实际状态重新规划。
5.  必要时自主选择挖掘障碍、放置平台或搭建支撑等地形改造方式。
6.  通过多段路线持续推进，直到真实抵达目标。
7.  只有确认无法安全继续，才向 Agent 返回终止结果。

规划和执行必须保持一致：路线是预测，不是事实；执行结果应由游戏中的实际位置、碰撞和地形状态验证。

导航内部可以采用不同层次的规划： -
区域/落脚面层：帮助理解地形结构和较大范围的可达关系。 -
运动规划层：结合角色物理状态，验证具体移动动作。 -
地形改造层：评估挖掘、放置平台或方块对通行路线的帮助。

这些是职责方向，不要求必须拆成同名类或独立项目。具体模块边界由实现时结合现有代码决定。

## 5. 分阶段实施

### Phase 1：持续导航与路线接续

**目标：**
一次目标请求能够跨越多次局部搜索持续推进，不因单次搜索预算或中间路线结束而过早失败。

重点改善： - 导航任务的持续生命周期。 - 完整路线与部分路线的处理。 -
路线执行跟踪、交接和下一段规划。 - 对搜索结果和实际执行失败的记忆。 -
从真实玩家状态恢复规划，避免反复尝试相同失败路线。 -
清晰区分内部搜索状态与 Agent 可见的最终任务状态。

继续利用现有物理预测、原生碰撞和移动/挖掘/放置执行能力。优先完成这一阶段，不要求同时实现完整地形拓扑或多步改造联合搜索。

### Phase 2：Surface Graph 与多尺度导航

**目标：** 让导航更有效地理解 Terraria
的地形结构，并扩大复杂地形中的搜索能力。

重点研究和实现： - 落脚面、平台、半砖、斜坡及可站立区域的表达。 -
不同落脚区域之间的候选连接关系。 -
结合物理模型验证跳跃、行走、下落等路线。 - 由局部向更大区域扩展搜索。 -
地形变化后更新受影响的路线信息。

Surface/区域拓扑用于缩小和组织搜索空间；具体动作仍需符合 Terraria
的真实运动与碰撞规则。

### Phase 3：移动与地形改造的统一规划

**目标：**
让导航能够整体权衡绕行、挖掘、铺平台和搭建支撑，而不局限于每次选择一个局部改造动作。

重点改善： - 评估连续地形改造的整体收益和成本。 -
复用现有原生挖掘与放置执行器。 -
改造后根据实际世界变化更新路线并继续导航。 -
让材料、危险和改造代价参与路线选择。

### Phase 4：特殊运动能力

**目标：** 根据实际需求逐步扩展不同运动方式。

可研究绳索、钩爪、翅膀/飞行、坐骑、液体环境及 Mod
提供的特殊移动能力。每种能力应依据真实运动机制参与规划，不应简单套用普通地面移动模型。

## 6. Agent 工具行为与结果

Agent 提供最终目标，不负责选择中间
Waypoint，也不负责处理导航器内部的搜索预算和路线恢复。

导航应向 Agent 提供清晰的任务结果： -
**completed**：已经通过实际游戏状态验证抵达目标。 -
**failed**：确认无法安全继续，并说明主要原因及已尝试的恢复方向。 -
**unknown**：当前无法可靠确认世界或执行状态，停止继续操作。

部分路线完成、重新规划、搜索预算耗尽等属于导航内部进度，不应被误报为整个任务完成或失败。

## 7. 验收方向

实施时应通过真实游戏场景验证，而不只依赖固定隔离场景。重点覆盖： -
目标超出单次搜索范围时，单次请求仍能持续推进。 -
搜索预算耗尽但存在可行前进路线时，导航能够继续。 -
候选路线执行失败后，能够调整策略而不是反复重试。 -
实际玩家状态偏离预测时，能够从真实状态恢复。 -
多段路线交接不会提前结束根导航任务。 -
平台、跳跃、落下和不同支撑地形能够正确处理。 -
必要时能够自主挖掘或搭建通路。 -
只有实际抵达并满足目标落脚条件时才报告成功。 -
取消、超时和状态未知时，能够正确停止动作并释放输入。 - 现有
`mine_target`、放置和普通移动能力保持回归通过。

测试结果应能说明导航是否持续取得实际进展、失败后是否改变策略，以及最终是否真实抵达，而不只是报告搜索器运行成功。

## 8. 实现协作原则

本文定义目标能力、架构方向和阶段边界，不规定不必要的内部实现细节。

实现时应： - 先审查当前代码，优先复用已有可靠能力。 -
根据现有结构选择合适的类、接口、数据结构和算法。 - 参考 Numen 与
TerraBot 的设计思想，结合 Terraria 实际机制适配。 -
将真实游戏风险与实现方便性区分开；避免把任意的小窗口、固定动作数量或单次搜索预算变成导航能力上限。 -
每个阶段完成后进行针对性真实场景验收，再进入下一阶段。

**本项目的设计责任是明确导航应该具备什么能力；具体如何在现有代码中实现，由
Codex 根据代码现状作出合理工程决策。**
