# M1.1 基础身体控制设计

-   **项目**：Terraria AI Companion
-   **状态**：设计决策记录（供实现前对齐，不是实现任务）
-   **版本范围**：M1.1-A 直接输入控制；M1.1-B 基础地面跟随
-   **参考代码快照**：
    -   Terraria AI Companion：`64aaef1`
    -   TerraBot：本对话上传的 `terrabot.zip` 反编译源码
    -   Numen：`61994fc00dd5f3fc963978362f156237f3801596`

------------------------------------------------------------------------

## 1. 目标

让 Agent 能够像真人一样操纵 Terraria
角色。移动不应被单一导航器、预测器或某种移动策略的适用范围限制。

M1.1 先建立基础身体控制能力：

1.  Agent 可以直接控制原生移动输入。
2.  一次输入可以持续多个游戏更新，不需要 LLM 逐帧调用 API。
3.  Terraria 原生物理负责加速、减速、重力和碰撞。
4.  Agent 能根据动作回执和后续观察决定下一步。
5.  在此基础上增加独立的基础地面跟随策略，减少常规移动时的模型决策次数。

M1.1 只针对基础移动能力。翅膀、钩爪、火箭靴、坐骑、额外跳跃和特殊移动
Buff 留待后续阶段适配。

## 2. 已确定的架构决策

### D1：Direct Input 是永久保留的基础能力

Direct Input 是 Agent 对角色的底层控制原语，不是临时过渡方案。

-   Agent 可以直接发出左、右、跳跃等原生输入。
-   不依赖 A\*、`PhysicsSimulator` 或 `LandingRegion`。
-   不要求角色必须处于地面或具有导航器要求的支撑宽度。
-   可以主动改变方向、跳跃、走下平台或进入下落状态。
-   后续增加 Ground Follow、Traversal、Recovery 或更复杂导航，都不能移除
    Direct Input。

Direct Input
的"自由"不意味着绕过角色身份、世界会话、控制租约、输入释放和动作互斥等系统控制约束。这些约束保护的是控制权正确性，不应被地形预测器的适用范围替代。

### D2：Ground Follow 是独立移动策略

Ground Follow 用于常规地面移动，不是 Agent 移动能力的总入口。

-   它可以在适用时接管一段普通地面移动。
-   它可以使用局部地形信息判断当前是否适合采用该策略。
-   不适用时应返回"本策略不接管 /
    需要其他策略"，而不是宣告角色无法移动。
-   Agent 仍可选择 Direct Input；未来也可交给
    Traversal、飞行、钩爪或其他策略。

**某个策略不能处理某种地形，不等于角色不能尝试通过该地形。**

### D3：游戏原生物理是运动结果的权威来源

移动通过原生输入驱动 `Player.Update`。Mod
不应通过直接设置位置或速度来伪造行走、跳跃或下落结果。

停止输入与角色停止运动是两个不同事件：

-   `inputReleased`：AI 控制输入已经释放。
-   `settled`：角色速度和落地状态满足稳定条件。

释放输入后，水平惯性应由 Terraria 自己处理。Direct Input
的取消不应默认把 `velocity.X` 清零。

### D4：按控制频率分层，不让 LLM 逐帧参与

-   **LLM**：决定目标、策略和遇到问题后的下一步。
-   **Lua**：编排多段动作、条件判断和观察。
-   **C# 游戏线程**：持续注入输入、采集必要状态、处理取消和控制权变化。

一次 Lua 移动调用可以对应多个
`Player.Update`。每个游戏更新不应产生一次模型请求，也不应要求一次 TCP
往返。

### D5：移动能力不能绑定固定速度假设

`max_updates` 表示输入持续的游戏更新数，不代表固定距离。

未来控制器需要根据运行时实际生效的运动参数和状态适配角色成长，例如：

-   `velocity.X`
-   `runAcceleration`
-   `runSlowdown`
-   `maxRunSpeed`
-   `jumpSpeed`、`jumpHeight`
-   翅膀、额外跳跃、坐骑及相关状态

优先读取游戏运行时的有效参数，不仅根据背包或装备名称推断能力。M1.1-A
的原始输入不需要先建立完整的 MovementProfile；M1.1-B
再验证基础速度反馈与制动。

### D6：区分系统执行失败与正常游戏结果

撞墙、没有前进、掉落、受伤等可能是正常游戏行为或策略结果，不应一概变成动作系统失败。

例如，输入任务按时结束但角色撞墙，应返回任务正常结束及 `no_progress` /
碰撞观察，而不是把它伪装成 IPC 或导航故障。

控制权丢失、角色身份变化、无法确认输入是否释放等系统不确定情况，仍应遵守现有
`unknown` 和隔离机制。

## 3. 当前项目基线（`64aaef1`）

以下是对该提交实际源码的核对，不代表这些能力已经满足 M1.1。

### 3.1 可复用的控制接入点

`CompanionBridge/ServerPlayerRuntime/ActorControl.cs` 定义了
`IMovementDriver`：

-   `Running`
-   `Matches(Player)`
-   `BeforeMovement(Player)`
-   `Update(orig, player, slot)`
-   `Retire(Player)`

`ServerAiNavigation` 实现了该接口。`ActorControl.Update`
在受控更新中调用原生
`Player.Update`，移动输入在审计过的原生更新边界注入。

这为新增移动驱动提供了现有接入点，但不意味着现有 `ActorControl`
的动作语义可以原样复用。

### 3.2 现有实现并不是通用 Direct Input

当前 `ActorControl` 的旧控制路径有明显限制：

-   `Inputs(Player, bool right)`
    只表达向右或不向右，不能表达完整方向与跳跃组合。
-   `Start` 要求水平速度接近零。
-   `Release(..., brake: true)` 会把水平速度清零。
-   `ActorAction` 以水平距离和更新次数为主要目标。

因此，M1.1-A
应复用其控制权、身份绑定、更新接管和生命周期经验，而不是继承这些单向移动、起步静止和强制制动语义。

### 3.3 现有导航路径仍依赖预测

-   `ServerAiNavigation` 通过 `NativeNavigation` 和 `PhysicsSimulator`
    规划、执行并核验路线。
-   `LocalMotionController` 仍然按预测帧执行行走或跳跃；开始规划要求
    grounded。
-   `SafeGroundWalk.TryPlan` 仍调用 `PhysicsSimulator.Predict`，并要求
    `ph.IsBasic`、平地和安全支撑。它减少了部分 A\*
    调用，但不是原生按键控制。

因此 M1.1-A
应作为独立动作路径存在，不能把"先通过现有导航预测"作为直接输入的前置条件。

### 3.4 必须复用的系统约束

现有代码已有角色身份、世界会话、代次、控制租约、动作互斥、取消、输入释放和
`unknown` 处理。M1.1 应沿用这些已经验证的系统边界。

但应重新审视哪些是**控制权正确性约束**，哪些只是**旧导航策略的适用条件**，避免后者泄漏成所有移动操作的拒绝规则。

## 4. M1.1-A：Direct Input

### 4.1 职责

接收一组原生移动输入，并在有限数量的游戏更新中持续应用。

接口概念示例（字段名和最终协议待实现前核对）：

``` lua
move_input({
    direction = "right",
    jump_hold_updates = 8,
    max_updates = 60
})
```

这是输入原语，不是目标坐标导航：

-   不接受"到达 X/Y"作为必要参数。
-   不进行全局寻路。
-   不要求预测整段轨迹。
-   不保证到达目标。
-   不根据固定帧数承诺固定移动距离。

方向输入应采用明确、互斥的状态；跳跃输入应有清晰的持续时间和释放语义。是否同时暴露
`up/down`，需结合 Terraria
原生按键行为在实现时确认；基础验收至少覆盖左右和跳跃。

### 4.2 单次动作生命周期

1.  **Start**：验证身份、世界、控制权、动作互斥和参数；记录起始状态。
2.  **Tick**：每个原生游戏更新明确设置完整移动输入，再执行原生更新并采集轻量状态。
3.  **Cancel / Stop**：在合法控制权内释放所有 AI
    输入；不伪造位置，不强制清除自然惯性。
4.  **Result**：返回执行更新数、起止位置、结束速度、生命变化、落地/空中状态、输入释放状态及终止原因。

一次动作只能有一个明确的控制者。新请求不能静默覆盖正在执行的动作。

### 4.3 终止结果建议

  情况                       结果语义
  -------------------------- ---------------------------------------------
  达到 `max_updates`         正常结束
  撞墙或没有有效位移         正常结束并报告无进展/碰撞观察
  主动取消                   cancelled；核验输入释放
  死亡                       记录死亡终态并释放输入
  真人手动接管               终止 AI 输入并交还控制权
  世界、角色代次或租约变化   按现有隔离规则处理；不能确认时为 unknown
  游戏更新停止推进           需要单独的看门/超时设计；不能谎称已释放输入

`completed` 仅表示这段输入任务结束，不表示到达目标或完成游戏目标。

### 4.4 回执与日志

动作回执建议至少包含：

-   `actionId`
-   `status`、`reason`
-   `requestedInputs`
-   `updatesRequested`、`updatesExecuted`
-   `startPosition`、`endPosition`
-   `endVelocity`
-   `grounded` / `airborne`
-   `healthStart`、`healthEnd` 或 `healthDelta`
-   `inputReleased`
-   `settled`（可未知）
-   控制权/身份绑定结果

详细逐更新轨迹进入
Trace，不全部塞进模型上下文。模型默认拿到简洁摘要；需要诊断时再读取详细轨迹。

### 4.5 M1.1-A 验收

-   平地向左、向右持续移动。
-   原地跳跃。
-   同时方向移动和跳跃。
-   空中改变水平输入。
-   主动走出平台并自然下落。
-   撞墙或受阻时返回正常的无进展结果。
-   中途取消：输入释放，角色保留自然惯性。
-   死亡、手动接管、角色/世界身份变化、连接中断等生命周期测试。
-   一次 Lua 调用覆盖多个游戏更新；确认没有逐 Tick 的模型/API 往返。
-   记录首次输入延迟、实际更新数、输入连续性、取消至输入释放延迟和最终状态完整性。

A 阶段不验收自动越障、任意坐标到达或脱困能力。

## 5. M1.1-B：Ground Follow

### 5.1 职责

Ground Follow
是一项基础移动策略：在适合普通地面移动时，根据目标水平位置持续控制方向，并结合实际运动状态调整输入。

它不是全局导航器，也不是 Direct Input 的替代品。

建议具备：

-   根据当前位置与目标方向选择左右输入。
-   观察实际水平速度和位置变化。
-   接近目标时考虑自然减速和制动距离。
-   发现持续无进展时停止盲目重复，向上层返回诊断。
-   当前局部条件不适用时交还控制权，让 Agent 选择跳跃、Direct Input
    或其他策略。

### 5.2 速度与制动

不能把"移动 N 帧"等同于"移动固定像素"。

后续 Ground Follow 应根据角色实际状态调整，例如使用当前
`velocity.X`、`runAcceleration`、`runSlowdown`、`maxRunSpeed`
估计加速与制动行为。

TerraBot 的 `BotFollowArrival` 使用当前水平速度和 `runSlowdown`
估算停止距离，并进一步验证预计停下的位置是否有支撑。这是值得研究的思路，但公式和阈值必须在
Terraria 实机中重新验证，不能直接当作精确物理定律。

### 5.3 进展监控

进展不能只看与最终目标的距离。至少应考虑：

-   目标距离是否显著改善。
-   是否进入新的空间区域。
-   垂直方向是否取得有效进展。
-   是否反复停留在同一位置。
-   目标、地形或角色能力是否发生变化。

无进展应产生可解释的状态，而不是简单增加重试次数。地形或能力变化后，应重新评估旧结论，不把一次失败永久记为不可达。

### 5.4 策略交接

后续可由协调器选择 Direct Input、Ground Follow、Traversal、Recovery
等策略，但 M1.1-B 不要求一次实现完整协调器。

需要先确立统一语义：

-   策略接管并执行。
-   策略不适用，允许其他策略尝试。
-   策略执行后无进展，返回观察与诊断。
-   系统控制权不确定，进入既有安全隔离流程。

普通游戏行为失败不能自动等同于系统级 `unknown`。

### 5.5 M1.1-B 验收

-   基础角色在平坦地面上向左右目标移动。
-   接近目标时不会因固定帧数而明显过冲；制动行为随实际速度变化。
-   移动受阻时能报告无进展，不无限重复。
-   目标或地形变化后能重新评估。
-   Ground Follow 不适用时，Direct Input 仍然可用。
-   不要求 A\* 为每段普通平地移动生成路线。

复杂墙体、长距离垂直移动、翅膀、钩爪、坐骑和特殊 Buff 不属于本阶段验收。

## 6. 参考项目：借鉴内容与边界

### 6.1 TerraBot（本对话上传的 `terrabot.zip`）

#### `BotFollowGround`

源码显示它不是单纯无条件按住方向键：

-   默认目标水平距离阈值为 100px。
-   要求 grounded。
-   `Walkable` 向前检查 16 步，每步 4px，局部范围约 64px。
-   每步尝试 0～16px 的垂直偏移，检查身体净空、支撑/斜坡和液体。
-   它只设置左右输入，并关闭跳跃与自动跳跃；跳跃越障由其他逻辑处理。
-   该控制器以 4px 水平位移或 Tick 连续性更新进展；24 Tick 无进展后进入
    90 Tick 冷却。

**借鉴**：地面跟随可以是轻量、局部、独立的控制策略，不必每次做全局 A\*。

**边界**：它自身仍有地面、支撑和液体适用条件。不能把这些条件变成 Agent
的总移动限制；不适用时应允许其他策略接手。

#### `BotFollowProgress`

源码显示：

-   目标变化超过 X 512px 或 Y 192px、超过 120 Tick
    未调用、或能力签名变化时重置监控。
-   与目标距离改善至少 16px，或进入新的空间格（X 32px、Y
    16px）时，记录进展。
-   240 Tick 无新进展后开始退避，失败次数最多 4 次，退避时间按 120 Tick
    递增。
-   退避期间每 30 Tick 检查局部地形哈希变化，地形变化会触发重新评估。

**借鉴**：用空间进展补充目标距离，避免把必要绕行误判为停滞；地形变化后重新评估。

#### `BotFollowRecovery`

源码显示它是跟随导航未解决时的有界恢复尝试：

-   使用 `BotAirNavigation.FindLocal` 生成局部路线。
-   整个恢复尝试最多 720 Tick。
-   90 Tick 没有改善局部目标距离时，反向移动 16 Tick，再重新搜索。
-   路线节点推进后重新计算进展基线。
-   检测到岩浆时终止本次尝试并冷却。

**借鉴**：恢复应是有时限、有反馈、可重新评估的动作。

**边界**：它不是通用矿坑脱困方案，也不能保证返回原路。M1.1 不实现完整
Recovery。

#### `BotFollowTraversal` 与 `BotFollowArrival`

-   `BotFollowTraversal.Observe` 读取
    `Player.jumpSpeed`、`Player.jumpHeight`，并记录部分装备签名。
-   轨迹计算使用 `runAcceleration`、`maxRunSpeed`、当前速度等实际参数。
-   `BotFollowArrival.SafeCoast` 根据当前速度和 `runSlowdown`
    估算停止位置，并检查落点。
-   `BotBrain.FollowCapabilitySignature`
    混合翅膀、液体状态（可选）、防摔标志、护甲与杂项装备类型。

**借鉴**：部分运动策略可以读取运行时参数；能力变化应触发重新评估。

**边界**：能力签名并不等于完整运动能力模型；Traversal
中仍有对湿润、坐骑、翅膀、额外跳跃等状态的适用限制。不要将其误认为已经实现通用装备适配。

#### 控制器组织方式

`BotBrain` 按顺序协调多个控制器，Ground、Traversal、Arrival、Recovery
并非彼此完全独立运行的
Agent。我们借鉴其职责拆分和显式交接，不照搬"跟随真人玩家"的目标管理逻辑。

### 6.2 Numen（固定提交 `61994fc...`）

#### `Trip`

-   一趟移动具有持续生命周期：`IDLE`、`DRIVING`、`CONSENT`、`DONE`。
-   每 Tick 推进当前导航。
-   一段导航结束后记录实际报告。
-   某格在执行时被权限或服务端拒绝，可以在本趟中将其作为墙并重新规划。
-   到达由目标自己的判据决定，不用模糊的"差不多到了"。

**借鉴**：持续任务生命周期、真实执行报告、失败后的有界重规划。

#### `UnstuckChain`

-   只在当前 `Trip` 存在且确认没有进展时触发。
-   直接通过按键进行 30 Tick 的短暂挣脱，不依赖导航或挖掘计划。
-   结束后有 40 Tick 冷却，让原任务从新位置重新尝试。

**借鉴**：直接按键控制可以作为高层导航之外的恢复反射。

**边界**：这是短时 best-effort 行为，不是安全路径证明；M1.1
不直接照搬随机方向挣脱。

## 7. 分阶段实施顺序

### M1.1-A：Direct Input

先完成输入原语、动作生命周期、取消与回执，并通过实机基础矩阵。

### M1.1-B：Ground Follow

在 A
已可靠工作的基础上，增加普通地面移动策略、速度反馈、制动和进展监控。

### 后续阶段（本设计不提前锁定实现范围）

再根据实机证据决定是否引入：

-   Traversal：跳跃越障、平台、落差和其他垂直移动。
-   Recovery：卡住后的有限恢复与环境经验。
-   Movement Profile：装备、Buff、翅膀、钩爪、坐骑等能力适配。
-   Frontier Exploration：使用持久化地图进行自主探索。

这些能力不应成为 M1.1-A 的前置依赖。

## 8. 实施前需要 Codex 核对的开放问题

以下问题尚未在设计层面完全定案，应该结合仓库当前实现与 Terraria
原生行为确认：

1.  新 Direct Input 与现有
    `ActorControl.IMovementDriver`、`ServerAiNavigation`
    的调度关系，如何保证同一角色只有一个输入所有者。
2.  `up/down` 是否纳入第一版输入字段，以及 `down+jump`
    穿平台的原生语义。
3.  跳跃输入的按住、释放、再次触发语义，如何避免残留 `controlJump` /
    `releaseJump` 状态。
4.  动作按游戏更新数结束时，输入释放与最终状态采样的准确时序。
5.  游戏更新停止推进时，外部看门机制如何报告超时；不能在游戏线程无法执行时虚报输入已释放。
6.  现有 `ActorControl.Healthy`
    对坐骑、冻结、蛛网等状态的限制，哪些属于系统正确性约束，哪些应由具体移动策略判断。

这些是实现前需要核对的边界，不应借此扩大 M1.1 的目标范围。

------------------------------------------------------------------------

## 9. 最终验收原则

M1.1 的成功不以"导航器能否找到所有路线"衡量，而以以下事实衡量：

-   Agent 能够直接、连续地操纵角色。
-   输入持续期间不需要 LLM 逐帧调用 API。
-   角色运动由 Terraria 原生物理产生。
-   普通移动策略失败，不会封锁 Direct Input。
-   移动结果能让 Agent 理解并决定下一步。
-   角色能力变化时，控制器能根据实际状态重新评估，而不是依赖固定帧数和固定速度假设。

**最终方向：让导航和自动移动帮助 Agent 玩游戏，而不是让 Agent
为了服从导航器而改变自己的玩法。**
