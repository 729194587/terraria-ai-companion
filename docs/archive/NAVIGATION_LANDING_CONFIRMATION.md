# 东向步行落点确认修复：0.1.53

PR #25，当前开发线。原实机记录 `runs/20261027-east-walk/` 保留不变；前四段成功，第五段失败，尚未重走该世界验收新版。

## 已定位的根因

原第五段目标 x=34475.117，失败点 (34391.406,3350)。预测与实际位置、速度均一致：Vx=2.8799992、Vy=0.33129883，MaxError=0。因此这份记录不能支持“轨迹已经数值发散”的判断。

原 `PhysicsSimulator.Predict()` 的步行前缀选点仅跳过 `Grounded=false` 的帧。原生 `NativeMotionWorld.Move()` 会把向下碰撞裁剪也标为接触，即便仍有非零 Vy；StateSpacePlanner 的交接回退只另查 SafeLanding，没有要求垂直速度归零。于是尚未确认稳定支撑的帧也可能成为移动交接点。

实际执行时，步行前缀耗尽后 LocalMotionController 直接清空计划；NavigationTask 将 NeedsPlan 当成交接时机，立即检查实际 Grounded / SafeLanding / 速度与位置。如果支撑尚未确认，直接 failed，且 ActualLanding 尚未填写。ServerAiNavigation 当时把所有该类失败作为普通 failed 发布，Stop 清理把 Vx 设为0、释放输入，但刻意保留 Vy 和重力。这解释了“回执vx=0、vy仍非零、动作却结束”。

旧任务最后一次后续地形查询 grounded=true；它并非失败瞬间的独立稳定落地点证明。原快照未记录那一刻的 Grounded/支撑拒绝详情，不能追溯断言究竟是哪一个支撑条件拒绝，也不能仅凭非零Vy断言完全离开坡面。能确认的是：预测与实际数值匹配，交接点不满足安全落地确认，旧终态却没有表达这种不确定性。

## 最小修复和状态语义

- 规划复用 `SupportedCheckpoint`：接触、垂直速度≤0.1、跳跃已释放/计数归零、原有 SafeLanding 同时满足。步行前缀沿已验证的预测/刹车尾段找到合格交接点；最终稳定预测也不再仅凭 Grounded/Vx 计数。未改碰撞实现、路线搜索目标或距离容差。
- 若执行到交接点仍缺少落地证明，NavigationTask 进入 `confirming_landing`。不重放前缀、不重新规划、不跳跃，返回中性输入，让原生制动/重力继续演化；保留原计划/代次/目标和观测。
- 至少连续两帧实际安全支撑、零附近水平/垂直速度、跳跃已释放，才填写 ActualLanding。位置仍须满足既有8px/4px容差；停在不同位置时是“已确认落地但预测不符”的普通失败，保留实际落点，不悄悄接管另一个落点。
- 观察最多60次自然物理更新。确认不到或出现危险观察，任务以 unknown 结束，ActualLanding仍为空；原外层绝对截止时间、取消和退休仍生效。不保证暂停/卡顿时60帧等于一秒，也不无限等候。
- 正常移动交接点仍按原位置/速度核验并立即交接，不每段强制停稳；确认后的边仍进入既有进度/次数预算，继续原任务而非启动重试。
- 原生层失败/异常时，若实际仍未确认安全落地，公开终态使用 `unknown / native_navigation_landing_unconfirmed`，reasonDetail 保留内部失败原因。已确认安全支撑的普通路线失败仍 failed。显式取消和超时继续使用 cancelled/timeout，不延迟取消来等待落地。
- 清理仍只释放输入、按原约定制动Vx；不传送、不修改Vy、不伪造落地。新增 grounded、safeSupport、settled、velocityBeforeRelease、observedGameUpdate。终态位置/速度和这些字段来自同一清理后观测，固定保存；旧导航快照中的 ObservedVelocity 是清理前物理更新，二者明确区分。
- 成功必须仍有安全停稳证明；释放输入、endEvidenceStatus=known 不证明已落地或无风险。Agent遇unknown应停止当前程序、查真实角色状态，不盲目重试。

共享任务的unknown也接入现有真人动作监督，避免被忽略后等到超时；日志只在进入确认/终态时记录，不每帧刷落地日志。失败跳跃不再将未确认坐标填入ActualLanding，实际位置仍留在ObservedPosition。
