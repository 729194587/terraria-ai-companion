# Terraria 自主导航 Phase 3：移动与地形改造的联合规划

**版本：** 1.1（简化版设计与实现规范）\
**前置阶段：** Phase 1 — 持续导航与路线接续；Phase 2 — Surface Graph
与多尺度导航\
**代码审查基线：** `codex/unified-autonomous-navigation`，提交
`568a50d26790d0cc4198dea8c88a4040805ec909`\
**架构依据：**
`terraria_navigation_architecture_v0.2.md`、`terraria_navigation_phase2_surface_graph.md`

> 本阶段先实现实用、可验证的局部改造规划，不预先建设复杂的通用规划框架。后续根据实际场景、性能和失败案例再逐步优化。

------------------------------------------------------------------------

## 1. 阶段目标

让导航能够比较两类方案：

- 在当前地形上直接移动或绕行；
- 通过挖掘障碍、放置支撑物，形成一条更合适的通路。

规划不再只判断“眼前这一格能不能挖”，而是能够评估一小段连续改造，例如先挖开数格，再放置支撑，最后从新形成的落脚区域继续移动。

本阶段重点是让移动、挖掘和放置能够进行合理的整体成本比较。**不要求第一版就实现完整的通用联合
A*，也不要求提前解决所有地形组合。*\*

### 完成后的基本能力

1.  比较现有移动路线与局部地形改造路线。
2.  评估连续数步挖掘、放置及其组合。
3.  估算移动、挖掘、放置和材料消耗的成本。
4.  识别明显不安全或当前无法可靠判断的改造。
5.  每次只执行下一项动作；确认真实效果后更新地形并重新规划。

------------------------------------------------------------------------

## 2. 当前实现与主要缺口

以下以提交 `568a50d` 的代码为基线。

| 现有模块                            | 当前职责                                          | Phase 3 的用途               |
|-------------------------------------|---------------------------------------------------|------------------------------|
| `SurfaceGraph` / `SurfaceNavigator` | 从当前真实地形生成落脚区域和移动连接              | 继续提供常规移动路线         |
| `NavigationTask`                    | 规划并执行移动，验证落脚，处理偏离和恢复          | 继续负责真实移动             |
| `NativeNavigationEdits`             | 检查局部挖掘、开路和支撑放置方案                  | 扩展为连续改造候选的评估入口 |
| `AutonomousNavigationTask`          | 组织移动、挖掘、放置、等待和重新观察              | 继续负责整个导航任务         |
| `ActorMining`                       | 通过 Terraria 原生流程执行挖掘并确认结果          | 继续作为挖掘执行入口         |
| `ActorPlacement` / `ActorItemUse`   | 通过原生物品使用流程执行放置并核对消耗            | 继续作为放置执行入口         |
| `NativeMotionWorld`                 | 使用真实 `Main.tile` 和 Terraria 原生碰撞验证移动 | 继续作为真实移动的验证依据   |

当前局部改造逻辑已经能够检查目标、工具、材料、交互距离和部分支撑条件，但主要还是围绕单次开路动作进行判断。成本估算也比较粗略，尚不能充分比较“绕行”与“连续挖掘/放置后再通行”的总代价。

因此，Phase 3 的主要增量是：

- 能够评估一小段连续改造，而不只评估当前一步；
- 能够估算改造后的后续通行成本；
- 能够把改造成本与现有移动路线放在一起比较。

## 3. 参考项目的借鉴范围

### Numen

Numen 的主要参考价值是：

- 将挖掘、放置表示为有顺序的规划动作；
- 在只读的虚拟地形视图上叠加假想改动；
- 后续动作依据此前改造后的地形进行判断；
- 将工具、材料和动作时间纳入成本比较；
- 记录真实发生的改造结果，而不是只记录计划意图。

Numen
的完整搜索和成本体系不需要在本阶段整体照搬。尤其不必一开始就实现复杂的持久化搜索状态、通用改造历史管理或完整地形模拟。

### TerraBot

TerraBot 的参考价值主要在 Terraria 场景：

- 地形改造前的安全检查；
- 支撑和平台放置；
- 材料与工具检查；
- 原生动作执行后的结果确认；
- 改造后重新观察和恢复导航。

TerraBot 的局部恢复策略也不等于完整的移动/挖掘联合搜索。

### 本项目的取舍

第一版采用简单组合：

- 保留当前 Surface Graph 和移动规划；
- 扩展现有局部改造规划；
- 使用轻量的局部虚拟地形评估连续改造；
- 继续复用现有原生挖掘、放置和移动执行器；
- 每次改造完成后重新观察并规划。

## 4. 第一版实现思路

不新增一套复杂的导航运行时，也不要求把整个世界的移动和地形改造放进同一个大型搜索空间。

建议流程：

1.  从当前真实地形获取现有移动路线及其成本。
2.  如果移动路线不存在或明显不理想，生成少量局部改造候选。
3.  候选可以包含连续挖掘、连续放置，或两者组合。
4.  在局部虚拟地形上按顺序检查候选动作，估算改造后是否能够继续通行。
5.  估算每个候选方案的总成本，与当前移动路线比较。
6.  选择较合适的方案，只执行下一项动作。
7.  等待原生动作完成，确认真实地形变化。
8.  更新受影响的 Surface Graph 信息，从真实玩家状态重新规划。

候选生成可以先使用有限深度、有限范围和少量规则，不需要一开始就采用通用
A\* 搜索所有可能的改造序列。

如果简单方案在实际场景中遇到明显局限，再考虑增加搜索能力。

------------------------------------------------------------------------

## 5. 局部虚拟地形

为了判断连续改造后的效果，需要一种轻量方式表达“如果这些 Tile
被挖掉或放置，局部地形会变成什么样”。

第一版只需覆盖当前候选涉及的局部 Tile，不需要复制整个世界。

### 基本要求

- 记录候选中计划挖除和放置的 Tile。
- 后续动作检查时，能够看到前面动作造成的假想变化。
- 不同候选方案之间互不影响。
- 未知或无法可靠判断的 Tile 不得直接当作空气或安全支撑。
- 放置方块与平台应保留不同的支撑语义。

### 重要边界

当前 `NativeMotionWorld` 的碰撞检查读取真实
`Main.tile`，并不会自动读取虚拟地形。

因此：

- 虚拟地形只用于局部结构判断和方案估价；
- 不能把虚拟地形上的路线标记为已经通过 Terraria 原生碰撞验证；
- 不要为了模拟候选方案而临时修改真实 `Main.tile`；
- 实际改造完成后，必须基于真实 Tile 更新 Surface
  Graph，并使用现有移动规划验证后续路线。

第一版不需要实现完整 Terraria 物理模拟器。

## 6. 成本模型

成本模型先保持简单，目的是让不同方案能够进行基本、可解释的比较。后续再根据实际执行数据调整估价精度。

### 6.1 成本单位

统一使用预计游戏更新数（Game Updates）作为主要时间单位。

移动、挖掘和放置都估算为完成所需的更新数。材料消耗和改造本身的额外代价，可以先使用简单的附加惩罚表示。

### 6.2 成本组成

**方案总成本 = 移动成本 + 挖掘成本 + 放置成本 + 材料惩罚 + 改造惩罚 +
后续路线成本**

| 成本项       | 含义                                           |
|--------------|------------------------------------------------|
| 移动成本     | 到达工作位置，以及改造后继续移动所需的预计时间 |
| 挖掘成本     | 挖除目标 Tile 所需的预计时间                   |
| 放置成本     | 使用物品并完成放置所需的预计时间               |
| 材料惩罚     | 消耗现有材料带来的额外代价                     |
| 改造惩罚     | 对不必要的挖掘或建造增加少量代价               |
| 后续路线成本 | 完成当前候选改造后，继续前往目标的预计成本     |

### 6.3 挖掘和放置估价

第一版可以沿用当前已有的粗略时间估算，并结合现有执行器信息逐步校准。

- 挖掘估价应考虑 Tile 类型、可用工具和原生镐力。
- 放置估价应考虑物品使用周期。
- 规划时选择的工具应与实际执行时使用的工具一致。
- `ActorMining`
  记录的实际更新数、挥动次数和挖掘进度，可以用于后续改进估价。

不要求第一版就精确模拟每一次原生挖掘伤害计算。

### 6.4 材料与安全

材料不足、目标不可挖、无法放置或目标位置不合法，属于不可执行条件，不应仅通过增加成本来处理。

未知地形、危险
Tile、无法确认的支撑变化以及当前无法建模的特殊碰撞，也应先排除或标记为未知，不得乐观地当作安全路线。

第一版不必建立复杂的风险评分体系。先把明确安全条件作为准入检查即可。

### 6.5 权重调整

第一版只需要能够区分明显不同的方案，例如：

- 很短的绕行通常不值得挖掘；
- 绕行代价明显较高时，可以考虑安全开路；
- 材料有限时，避免不必要的放置；
- 改造收益很小时，倾向于保留原地形。

具体权重不在设计阶段写死。后续根据实际到达率、改造数量和执行耗时调整。

## 7. 搜索范围与状态管理

第一版只在局部范围内生成有限数量的改造候选。

- 不搜索整个世界的任意挖掘和放置组合。
- 不要求实现通用的联合 A\*。
- 候选动作数量和搜索范围保持有界。
- 搜索预算用尽时，应表示本次评估未完成，不能直接认定没有路线。

候选方案需要保留自身的改造顺序。两个方案即使到达相同位置，只要此前改造不同，就不能在后续判断中错误地共用同一份虚拟地形。

这一点借鉴 Numen
对改造历史与搜索状态一致性的处理经验，但第一版可以用简单的候选对象或局部改动列表实现，不必提前建设复杂的持久化状态系统。

------------------------------------------------------------------------

## 8. 执行与重新规划

继续复用当前任务和原生动作体系：

- `AutonomousNavigationTask` 组织整个导航过程；
- `NavigationTask` 负责真实移动；
- `ActorMining` 负责原生挖掘；
- `ActorPlacement` / `ActorItemUse` 负责原生放置。

执行时不要一次性盲目完成整段假想方案，而应采用简单的滚动流程：

1.  选择成本较低的候选方案。
2.  只执行下一项移动、挖掘或放置动作。
3.  等待动作结束并确认结果。
4.  如果地形确实发生变化，记录真实变化并更新相关图信息。
5.  从当前真实状态重新规划后续动作。

如果动作失败、目标被外部改变或结果无法确认，不得继续执行依赖该结果的后续计划。

第一版不需要独立的复杂改造账系统。可以先复用现有动作结果和地形读取机制，只有在实际需要时再抽取统一记录结构。

------------------------------------------------------------------------

## 9. 阶段范围

### 本阶段实现

1.  对比现有移动路线和局部改造路线。
2.  评估有限长度的连续挖掘、放置及组合方案。
3.  使用轻量局部虚拟地形判断改造后的基本通行条件。
4.  建立简单、统一的时间与附加成本估算。
5.  保留必要的安全准入检查。
6.  复用现有原生动作执行器。
7.  改造完成后更新地形信息并重新规划。
8.  保持搜索范围和每次执行的动作数量有界。

### 本阶段不实现

- 全世界范围的任意地形改造搜索；
- 完整通用联合 A\* 或复杂的持久化搜索状态系统；
- 完整 Terraria 原生物理模拟器；
- 自动采集、制作或合成建筑材料；
- 通过修改真实 `Main.tile` 模拟虚拟地形；
- Phase 4 的绳索、钩爪、飞行、坐骑和 Mod 特殊运动。

## 10. 测试与验收

完整 Host & Play 导航验收仍按 Phase 2 文档的安排，在 Phase 1–4
全部实现后统一进行。本阶段先完成定向测试和回归测试。

### 10.1 方案选择

- 短距离绕行优于不必要的挖掘；
- 绕行代价明显较高时，能够选择安全改造；
- 连续挖掘和挖掘后放置能够参与成本比较；
- 材料不足时拒绝相应方案；
- 改造收益很小时，能够避免过度改造。

### 10.2 虚拟地形

- 连续挖掘后，后续判断能够看到已挖空的格子；
- 连续放置后，后续判断能够看到新支撑；
- 不同候选之间的假想改动互不污染；
- 未知或危险地形不会被乐观地视为安全；
- 虚拟地形评估不会修改真实 Tile。

### 10.3 原生执行

- 挖掘成功后确认真实 Tile 变化；
- 放置成功后确认 Tile 变化和材料消耗；
- 原生动作拒绝时，不把计划动作当作成功；
- 目标被外部修改时停止依赖旧计划；
- 动作结果未知时不继续执行后续动作。

### 10.4 改造后导航

- 挖掘后能够更新受影响的 Surface；
- 放置后能够发现新形成的支撑区域；
- 改造后从真实玩家状态重新规划；
- 旧路线或旧候选依赖的地形发生变化时能够重新评估。

### 10.5 回归测试

保持 Phase 1、Phase 2，以及现有
`mine_target`、`mine_tile`、`place_tile`、普通移动和安全落脚测试通过。

### 阶段完成条件

- 能够比较绕行与有限连续改造方案；
- 成本估算能够影响方案选择；
- 虚拟地形能够正确表达候选中的连续改动；
- 不安全或未知改造不会被当作可行路线；
- 真实改造通过现有原生执行器完成并确认；
- 改造后能够基于真实地形继续导航；
- 既有阶段和动作回归通过。

------------------------------------------------------------------------

## 11. 后续优化方向

以下内容留待第一版运行后，根据实际问题决定是否需要：

- 更准确的原生挖掘时间模型；
- 更细致的材料价值和保留策略；
- 更大的候选搜索范围或更复杂的搜索算法；
- 更完善的改造历史与缓存管理；
- 更准确的虚拟地形几何预测；
- 根据实际执行数据自动校准成本参数。

这些不是第一版的前置条件。只有当测试或实际运行证明简单方案不足时，再增加相应复杂度。

------------------------------------------------------------------------

## 12. 核心原则

**先让现有导航能够合理比较“绕行”和“有限地形改造”，并可靠地执行、确认和重新规划；不要为了预想中的扩展提前建设复杂系统。**

Surface Graph
继续理解当前真实地形，局部改造规划负责评估有限候选，虚拟地形负责表达假想变化，现有原生执行器负责真实改造，原生碰撞负责验证改造后的实际移动。
