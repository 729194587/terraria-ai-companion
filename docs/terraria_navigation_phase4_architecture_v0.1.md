# Terraria 自主导航系统 Phase 4 总体架构设计 v0.1

**状态：** 架构设计草案\
**适用范围：** Terraria 1.4.4 / tModLoader 运行环境\
**前置阶段：** Phase 1、Phase 2、Phase 3\
**设计参考：** Numen、TerraBot、Terraria/tModLoader 原生运动机制

------------------------------------------------------------------------

## 1. 设计目标

Phase 4
的目标是扩展现有自主导航系统，使其能够利用玩家当前实际具备的运动能力，在复杂地形中完成自主移动。

运动能力包括但不限于：

-   普通行走与跳跃
-   额外跳跃
-   翅膀与飞行
-   火箭靴与空中推进
-   坐骑
-   钩爪
-   绳索
-   液体环境中的运动
-   Mod 提供的其他特殊运动能力

本阶段的核心目标不是为每种装备单独编写导航逻辑，而是建立能够感知玩家实际运动能力，并将其纳入统一导航规划的架构。

## 2. 核心架构原则

### 2.1 导航系统负责运动决策

AI 负责提出目标位置和高层任务策略。

导航系统负责自主决定如何抵达目标，包括：

-   什么时候行走；
-   什么时候跳跃；
-   使用普通跳跃还是额外跳跃；
-   什么时候飞行；
-   什么时候使用钩爪；
-   如何组合不同运动方式。

跳跃、飞行和其他运动能力都是导航系统内部可以调用的移动能力，不应要求 AI
单独判断使用时机，也不应为每种运动方式增加独立的 AI 操作接口。

### 2.2 游戏原生运行时是能力事实来源

优先读取 Terraria/tModLoader 已经计算或注册的实际运动能力。

例如：

-   ExtraJump 注册体系；
-   WingStats 和实际飞行参数；
-   MountData 和坐骑状态；
-   Projectile 及钩爪扩展机制；
-   Player 当前物理参数；
-   Buff、装备和环境产生的实际运动效果。

不建立针对具体物品 ID、饰品 ID 或 Buff ID 的运动能力映射数据库。

新增装备如果使用已有原生扩展机制，系统应尽可能自动发现其能力。

### 2.3 能力发现与运动预测分离

能够发现一种能力，不代表已经能够准确预测它的运动轨迹。

系统必须区分：

1.  **能力已发现**：游戏中存在该能力。
2.  **状态已识别**：能够获取当前是否启用、是否可用、是否激活及其资源状态。
3.  **运动可预测**：具有足够可靠的运动模型。
4.  **导航可使用**：运动模型已经通过必要验证，可以参与路线规划。

只有满足导航使用条件的能力才能进入实际路线规划。

不能可靠预测的能力可以保留识别结果，但不能假装已经支持。

### 2.4 运动执行优先复用 Terraria 原生机制

导航系统负责决定运动方式和控制输入。

实际运动仍由 Terraria 完成，包括：

-   Player 更新；
-   碰撞检测；
-   跳跃机制；
-   飞行机制；
-   钩爪牵引；
-   坐骑运动。

不重复实现一套与游戏并行的运动执行系统。

### 2.5 运动预测与真实执行分离

搜索过程需要可重复、可控的运动预测模型。

不能在 A\* 搜索中直接反复调用完整
Player.Update，也不能让搜索过程修改真实 Player 或 Tile 状态。

预测结果必须经过真实执行验证。

预测与实际运动不一致时，应停止依赖旧预测的动作并重新规划。

## 3. 总体架构

系统沿用现有导航架构，扩展运动能力感知和运动模型。

### 3.1 架构组成

**A. Terraria 原生运行时**

提供玩家当前实际状态、物理参数、能力注册信息和环境状态。

**B. 有效运动状态采集（Movement State Capture）**

负责读取当前玩家实际具备的运动能力及其状态。

**C. 运动能力描述（Movement Capability Profile）**

统一表达当前运动能力、有效参数、剩余资源和状态变化。

**D. 运动模型（Movement Models）**

负责预测不同运动方式下的状态转换和可行轨迹。

**E. 统一导航规划器**

将不同运动方式纳入现有 Surface Graph 和物理状态搜索体系。

**F. 原生运动执行与验证**

通过 Terraria 原生输入执行动作，观察实际运动结果，并在必要时重新规划。

### 3.2 数据流

Terraria Player 当前状态\
↓\
有效运动状态采集\
↓\
Movement Capability Profile\
↓\
运动模型与状态转换预测\
↓\
Surface Graph / Physics Planner\
↓\
导航动作序列\
↓\
原生输入执行\
↓\
真实状态验证与重新规划

------------------------------------------------------------------------

## 4. 运动能力描述

### 4.1 基础物理参数

继续使用现有 MobilityProfile 和 PhysicsParameters。

负责表达实际生效的基础物理参数，例如：

-   水平加速度；
-   最大移动速度；
-   重力；
-   最大下落速度；
-   普通跳跃参数；
-   空中控制参数。

由游戏实际计算后的参数作为优先数据来源。

不追踪具体是哪件饰品或哪个 Buff 提供了这些基础属性。

### 4.2 离散运动能力

对具有独立激活、资源消耗或状态转换的运动能力进行描述。

例如：

-   ExtraJump；
-   翅膀飞行；
-   火箭靴推进；
-   冲刺；
-   钩爪；
-   坐骑特殊运动。

根据原生机制获取相应状态，不预先假设所有能力都具有相同字段。

### 4.3 环境运动状态

环境本身也会影响运动能力。

例如：

-   水中；
-   蜂蜜中；
-   岩浆中；
-   液体状态变化；
-   绳索附着；
-   平台和特殊支撑状态。

这些状态不应全部被错误地归类为装备能力。

### 4.4 能力状态变化

运动能力可能在一次导航任务中发生变化。

例如：

-   二段跳被消耗；
-   翅膀飞行时间减少；
-   火箭靴推进资源变化；
-   钩爪连接或释放；
-   坐骑状态改变；
-   装备或 Buff 改变有效物理参数。

这些变化必须能够影响运动状态快照，并使不再适用的旧规划失效。

------------------------------------------------------------------------

## 5. 运动模型与规划器

### 5.1 运动模型职责

每种复杂运动能力可以拥有自己的运动预测逻辑。

运动模型负责：

-   判断当前状态是否满足运动前提；
-   预测运动过程；
-   计算资源消耗；
-   预测运动后的物理状态；
-   判断可能的落脚区域；
-   提供规划器需要的状态转换信息。

不要求所有能力都使用同一套运动方程。

### 5.2 统一规划

不同运动模型最终接入现有导航规划体系。

规划器负责比较可行运动方案，并选择能够推进目标的路线。

例如，面对一个较高平台：

1.  尝试评估普通跳跃；
2.  如果普通跳跃无法通过，评估可用的额外跳跃；
3.  如果飞行能够通过，也可以评估飞行路线；
4.  根据可行性、运动资源和路线成本选择方案；
5.  执行后根据真实状态继续规划。

上述过程完全由导航系统完成，不需要 AI 参与运动方式选择。

### 5.3 规划状态

运动预测不能只记录位置和速度。

当某种能力的后续可用性依赖资源状态时，预测状态还必须包含相应信息。

例如额外跳跃是否已经使用、剩余飞行时间等。

避免两个物理位置和速度相同、但实际可用运动能力不同的状态被错误合并。

具体需要纳入哪些字段，由对应子阶段根据原生机制确定。

------------------------------------------------------------------------

## 6. 原生执行与验证

### 6.1 执行

继续复用现有：

-   Task Runtime；
-   原生 Player 输入；
-   导航执行器；
-   进度监测；
-   失败恢复机制。

导航规划器输出运动动作，执行层将其转换为 Terraria 原生输入。

### 6.2 验证

运动执行后，需要检查：

-   实际位置；
-   实际速度；
-   当前运动状态；
-   能力资源变化；
-   是否到达预测检查点；
-   是否成功落脚。

预测到达不能代替真实到达。

### 6.3 重新规划

出现以下情况时，应重新评估路线：

-   实际运动偏离预测；
-   能力资源发生变化；
-   装备或 Buff 改变有效物理参数；
-   能力失效；
-   环境发生变化；
-   运动模型不再适用。

保留 Phase 1 已有的输入释放、失败记忆、恢复和安全检查机制。

------------------------------------------------------------------------

## 7. Mod 扩展策略

Phase 4 应尽可能利用 tModLoader 已有的动态注册机制。

对于使用标准扩展机制的 Mod 能力，优先实现自动发现和参数获取。

但是，Mod 可以在扩展钩子中执行自定义逻辑，因此不能保证任意 Mod
的运动行为都可以自动预测。

采用以下策略：

1.  原生机制能够完整描述的能力，自动接入。
2.  能够获取参数且具备可靠预测模型的能力，允许参与规划。
3.  需要特殊运动逻辑的 Mod，可以在未来提供适配接口。
4.  无法可靠预测的能力，暂不参与自主导航。

不以支持所有 Mod 为第一版验收目标。

## 8. 子阶段规划

### Phase 4.1：动态能力发现与状态采集

建立统一运动能力感知基础。

主要目标：

-   研究并复用 Terraria/tModLoader 的能力注册体系；
-   获取当前实际生效的运动参数；
-   动态发现已注册的特殊运动能力；
-   读取能力状态和资源状态；
-   扩展现有 MobilityProfile；
-   建立运动能力变化检测和规划失效机制。

本阶段不要求完成所有特殊运动能力的预测与导航接入。

### Phase 4.2：额外跳跃（ExtraJump）

接入原生 ExtraJump 注册机制。

支持不同额外跳跃的状态识别、资源管理、运动预测和导航规划。

不针对具体跳跃饰品建立硬编码映射。

### Phase 4.3：翅膀与火箭靴

研究并接入：

-   翅膀飞行；
-   飞行时间；
-   空中水平控制；
-   火箭靴推进；
-   飞行与推进资源状态；
-   滑翔和降落行为。

### Phase 4.4：坐骑（Mounts）

接入原生 Mount 运动参数和状态。

研究不同坐骑的运动能力及其对现有规划器的影响。

### Phase 4.5：钩爪（Grappling Hooks）

接入钩爪发射、附着、牵引和释放等运动过程。

研究不同钩爪及 ModProjectile 的参数和运动行为。

### Phase 4.6：绳索与液体环境

扩展绳索攀爬及不同液体环境下的运动状态和规划能力。

### Phase 4.7：Mod 特殊运动能力

根据前面阶段的实际实现情况，建立必要的 Mod 运动模型扩展机制。

不要求自动理解任意 Mod 自定义代码。

以上子阶段是当前规划，后续可以根据原生机制研究和实现结果调整。

------------------------------------------------------------------------

## 9. 与 Phase 1--3 的关系

Phase 4 是现有导航系统的能力扩展，不是重新建设导航系统。

继续保留：

-   Phase 1：持续导航、路线接续、失败恢复；
-   Phase 2：Surface Graph、多尺度搜索；
-   Phase 3：移动与局部地形改造成本比较。

Phase 4 主要扩展：

-   MobilityProfile；
-   运动状态快照；
-   PhysicsState；
-   PhysicsSimulator；
-   StateSpacePlanner；
-   特殊运动的原生执行与验证。

具体修改范围由各子阶段详细设计决定。

## 10. 参考项目的借鉴原则

### Numen

重点借鉴：

-   BodySnapshot；
-   Mobility；
-   Kinematics；
-   运动预测与真实执行分离；
-   基于真实状态进行规划。

不直接照搬其 Minecraft 特定能力模型。

### TerraBot

重点借鉴：

-   Terraria 原生运动状态读取；
-   空中运动控制；
-   翅膀与火箭靴资源管理；
-   钩爪和绳索的实际执行机制；
-   原生物理行为和碰撞反馈。

不直接复制其针对具体装备或能力类型的硬编码判断。

### Terraria/tModLoader

作为运动能力和执行行为的主要事实来源。

优先研究和复用游戏内部函数、状态对象、动态注册体系及实际运行结果。

## 11. 总体验收目标

Phase 4 全部完成后，导航系统应当具备以下能力：

1.  能够识别玩家当前实际具备的运动能力。
2.  能够获取这些能力的有效状态和资源。
3.  能够将已验证的特殊运动方式纳入统一路线规划。
4.  能够自动选择普通移动和特殊运动方式的组合。
5.  能够通过 Terraria 原生机制执行实际运动。
6.  能够根据实际运动结果验证预测并重新规划。
7.  新增使用现有标准扩展机制的能力时，尽可能无需修改导航核心代码。
8.  对无法可靠预测的能力保持明确的支持边界。

最终目标：

**玩家只需向 AI
提供目的地，导航系统就能够根据玩家当前实际具备的运动能力，自主规划并执行抵达目标的路线。**

## 12. 后续工作约束

本文件是 Phase 4 总体架构约束，不是所有子阶段的详细实现说明。

后续每个子阶段应当：

1.  先研究对应 Terraria/tModLoader 原生机制。
2.  对照当前项目代码确定实际差距。
3.  编写该子阶段独立的详细设计文档。
4.  再交由 Codex 实现。
5.  根据设计文档进行代码审查和定向验收。

不提前规定尚未研究清楚的实现细节。

特别是原生 API、IL Hook 和游戏线程调用方式，必须以项目实际使用的
tModLoader 版本为准。

本阶段暂不要求进行最终图形 Host & Play
验收。完整导航系统的真实验收仍安排在 Phase 1--4 全部实现之后。
